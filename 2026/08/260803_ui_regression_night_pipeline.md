# 조용히 사라지는 것을 잡는 도구

> 타입체크도 린트도 유닛테스트도 다 통과하는데 화면에서 버튼 하나가 사라져 있다. 여러 에이전트가 동시에 커밋하는 환경에서 이런 회귀는 아무 신호도 내지 않는다. 매일 밤 22:30에 화면을 떠서 어제와 비교하고, 사라진 요소를 어떤 커밋이 지웠는지 지목해 아침에 알려주는 파이프라인을 만들었다.

## 배경

여러 에이전트가 동시에 커밋하는 개발 방식으로 옮겨오면서 새로운 종류의 회귀가 생겼다. 각 에이전트는 자기 일을 정확히 하고 검증도 통과하는데, 그 과정에서 기존 UI 요소가 조용히 사라진다. 공용 컴포넌트 한 줄을 고치면 그걸 쓰는 화면 넷에서 동시에 무언가가 없어지는 식이다. 타입은 맞고 테스트는 통과하니 아무도 모른다.

특히 `apps/web`이 `packages/*`를 임베드해 실행하는 렌더러 노드 라우트가 취약했다. 패키지 쪽 변경이 앱 화면에 어떻게 나타나는지는 실제로 띄워 봐야만 안다.

그래서 필요한 건 "매일 밤 화면을 실제로 띄워서 어제와 비교하고, 다르면 누가 그랬는지 지목하는" 도구였다. 문제는 이런 도구를 만들 때 흔히 저지르는 실수가 두 가지 있다는 것이다. 하나는 감시 대상 목록을 새로 정의하는 것이고, 다른 하나는 오탐이 많아 아무도 안 보게 되는 것이다.

## 핵심 내용

### 개별 작업 기록 (시간순)

- 야간 UI 회귀 감지 파이프라인 신설
  - 라우트 목록과 대기 기준을 새로 정의하지 않고 기존 하네스를 재사용했다. `harnesses/journeys/visual-capture-routes.json`을 읽기 전용 정본으로 쓰고, Readiness v2로 패키지가 완전히 마운트된 시점에만 스냅샷을 뜬다. **목록이 두 벌로 갈라지면 그 자체가 새로운 누락의 원인이 된다.**
  - 캡처는 ARIA 스냅샷을 날짜별 디렉토리에 저장한다. 실패한 라우트는 스냅샷을 남기지 않고 메타 파일에 사유만 기록한다. 빈 화면이 대량 REMOVED로 번지는 걸 막기 위해서다.
  - 분석은 REMOVED/ADDED/RENAMED로 분류하고 REORDERED는 집계에서 뺀다. RENAMED 승격은 REMOVED 계산 뒤에 하고, 유사도 문턱은 같은 슬롯일 때만 낮춘다. 전역으로 낮추면 진짜 삭제가 정보용으로 조용히 강등된다.
  - 귀속은 두 단계다. `git log -S` 히트는 확정, 라우트 의존성 glob 매칭은 추정으로 구분한다. 후보가 여럿이면 여럿 그대로 보고하고 단정하지 않는다.
  - 산출물은 사람용 리포트와 에이전트용 수정 프롬프트, 그리고 복원 완료 조건 스펙이다. private 레포로 push한 뒤 Teams에는 요약과 딥링크만 보낸다. diff는 보내지 않는다.
  - 오탐 방지 두 장치는 실측 사고 기반이다. design-web의 dist-lib 재빌드로 dev 인스펙터가 사라지며 REMOVED가 11건 터진 적이 있어서, 캡처 시점에 dev 오버레이를 끄고 소비 라이브러리 지문을 남겨 재빌드가 있었으면 커밋을 지목하기 전에 경고한다.
  - 22:30 실행이라 포트 강제 종료를 쓰지 않는다. 포트가 점유돼 있으면 작업 중일 수 있으므로 죽이지 않고 중단하며, 명시적 플래그로만 덮어쓴다.

- design·sds 계열을 1차 감시 범위에서 제외
  - 요청에 따라 데모 2개와 렌더러 노드·액션 2종을 뺐다. 그룹이 아니라 **라우트 이름 기준**으로 걸렀다. 노드·액션 라우트는 하나의 템플릿에서 확장되고 그 템플릿에 renderer-cad, renderer-design, renderer-sds가 전부 함께 달려 있어서 그룹으로 거르면 cad·modeler·report까지 같이 날아간다. 확장된 이름에는 stepId가 박히므로 이름이 유일하게 정확한 기준이다.
  - 제외는 조용히 일어나지 않는다. 콘솔 출력, 메타 파일, 리포트 본문의 "감시 제외" 섹션 세 곳에 남긴다. **이 도구가 막으려는 게 조용한 누락인데 제외 자체가 조용하면 앞뒤가 맞지 않는다.** 의존성 데이터의 design/sds 항목도 남겨 뒀다. 제외를 되돌리는 순간 귀속이 바로 동작해야 한다.
  - 함께 고친 것으로, 콜드 컴파일 때문에 첫 라우트가 readiness 타임아웃에 걸리던 문제가 있었다. 프로파일 타임아웃은 서버가 데워진 상태를 전제한 계약이라 늘리면 진짜 고장난 화면까지 오래 붙잡게 된다. 대신 첫 goto를 워밍업으로 삼아 reload 후 같은 계약 시간으로 한 번만 재시도한다. 기다린다고 해결되지 않는 사유는 재시도 대상에서 뺐다.

- 감시하지 않는 번들의 재빌드 경고 제거
  - design과 sds를 감시에서 뺀 뒤, 환경 변화 경고가 정확히 그 둘의 재빌드에 대해서만 뜨는 상황이 나왔다. 아무도 보지 않는 화면의 번들을 두고 "커밋을 지목하기 전에 확인하라"고 말하는 꼴이라 순수 노이즈였다.
  - 추적 대상 번들마다 영향을 줄 수 있는 라우트 이름 조각을 함께 선언하고, 그 조각이 실제 감시 목록에 걸릴 때만 경고하게 했다. 다시 감시에 넣으면 경고도 자동으로 되살아난다.

- 리포트에 프론트매터 추가, 같은 요소 여러 라우트를 묶어 표시
  - 리포트 문체가 "- 총 N건 변화 감지" 같은 불릿 조각과 em dash 위주라 부자연스러웠다. 제목을 정형 포맷으로, 본문을 완결된 문장으로 바꾸고 em dash는 괄호나 중점으로 대체했다.
  - 지식 그래프 구축용 YAML 프론트매터를 추가했다. 요소 단위로 묶은 findings, 비교 커밋 범위, 카운트, 제외 라우트, 미실행 라우트를 기계가 파싱할 수 있는 형태로 남긴다. **매일 밤 이 필드들이 쌓여야 나중에 "이 요소는 자주 사라진다" 같은 관계를 그래프로 엮을 수 있다.**
  - 사고 추정 표와 수정 프롬프트를 요소 단위로 묶었다. 실측에서 공용 Button 한 줄을 고쳤을 때 "button 로그인"이 4개 라우트에서 동시에 REMOVED로 잡혔는데, 라우트별로 10줄을 늘어놓으면 같은 사고가 10번 일어난 것처럼 읽혔다. 실제로는 원인 하나에 영향 라우트 여럿이다.
  - 단, 이름 없는 요소는 묶지 않는다. role+name만으로 묶었더니 한 라우트 안의 서로 다른 이름 없는 버튼 2개가 같은 라벨로 1개로 합쳐지는 미탐이 나왔다. 실제로는 2개가 사라졌는데 1개라고 보고한 것이다. **이름이 있을 때만 신뢰할 수 있는 동일성 근거가 있다.**

- 리포트 요약 굵게 + 비교 경계 커밋 작성자 표기
  - 주 요약 문단이 개수를 굵게 표시하지 않고 한 문장에 몰려 있어 항목별로 불릿을 나누고 건수를 굵게 표시했다.
  - 비교 대상 줄이 해시만 보여주고 있었다. 범위 안 개별 커밋의 author는 표에서 볼 수 있었지만 비교 자체의 경계(어제와 오늘 캡처 당시 HEAD)가 누구 손에서 일어났는지는 어디에도 없었다. 두 경계 커밋의 짧은 해시와 author를 조회해 리포트와 수정 프롬프트가 같은 문구를 쓰게 하고, 프론트매터에도 구조로 추가했다. 조회 실패 시에는 해시 없이 날짜만 보여준다.

- private 레포 README를 사고 추정 건수 표로 재구성
  - 레포 인덱스가 링크 나열뿐이라 정작 궁금한 심각도를 알려면 하나씩 열어봐야 했다. 각 리포트 프론트매터의 사고 추정 건수를 파싱해 표에 바로 노출한다. 프론트매터가 항상 같은 형식으로 찍히므로 정규식 하나면 충분했다.
  - 팀원 초대 안내를 계정 하나씩 넣는 예시 대신 반복문으로 바꿨다. GitHub private 레포는 자기가 알아서 접근을 요청하는 셀프서비스가 없어 오너가 계정을 정확히 지목해야 하는데, 최소한 반복 타이핑이라도 없애려는 것이다.

- 프론트매터에 심각도 추가, 커밋 정규화, 익명 ADDED 압축
  - 프론트매터가 그래프 구축 목적에 비해 너무 장황해 세 가지를 고쳤다.
  - 심각도를 도입했다. REMOVED가 아니거나 의도된 제거면 info, 이름 없는 요소는 무조건 low(자리만으로는 밤마다 같은 인스턴스인지 보장 못 한다), 확정 귀속이거나 렌더러 라우트면 high, 나머지는 medium이다. 리포트 표와 수정 프롬프트 제목에 반영했다.
  - 커밋을 정규화했다. 같은 커밋이 여러 요소를 건드리면 findings 안에 author와 subject 전체가 요소 수만큼 반복됐다. 전역 커밋 테이블에 hash 하나당 한 번만 적고 각 finding은 해시로 참조하게 바꿨다.
  - 이름 없는 ADDED 요소는 findings에서 빼고 개수만 남긴다. 그래프에서 같은 정체성으로 묶일 근거가 없는데 밤마다 수십 건씩 나올 수 있어 저장 부담 대비 정보 가치가 가장 낮다.
  - 스키마 버전을 2로 올렸다.

- private 레포 README를 슬로건 스타일로 다시 쓰고 초대 섹션 제거
  - 제목을 바꾸고, 무엇을 하는 도구인지를 설명문 대신 짧은 문구 나열로 표현했다. 팀원 초대 섹션은 뺐다. 오너만 보는 운영 절차라 방문자용 첫 화면에는 안 맞고, 초대 명령은 로컬 운영 문서에 이미 있다.

- run.sh가 .env를 실제로 로드하지 않던 문제 수정
  - Teams 웹훅 URL과 publish 레포, 웹 URL을 읽는 코드가 전부 `process.env`만 보는데 `run.sh`는 그 어디서도 `.env` 파일을 읽어 셸 환경에 심어주지 않았다. `.env`에 웹훅을 넣어도 `run.sh`로 실행하면 조용히 무시됐을 것이다.
  - 맥플로우가 다른 곳에서 이미 쓰는 표준 로더를 재사용해 각 단계 호출을 감쌌다. 새로 만들지 않고 재사용한 이유는 이미 검증된 파싱 규칙(주석과 따옴표 처리)을 그대로 쓰기 위해서다. 실제로 환경변수가 주입되는 것과 dry-run이 이 경로로도 도는 것을 확인했다.

- 사고 추정이 있으면 private 레포에 GitHub Issue 자동 생성
  - Power Automate 커스텀 흐름의 HTTP 트리거는 Premium 라이선스가 있어야 동작한다는 걸 확인했다. 조직 계정에 없으면 그 자리에서 막힌다. 대신 GitHub 공식 Teams 앱을 채널에 추가해 레포를 구독하면 Issue가 열릴 때마다 카드가 자동으로 뜬다. Power Automate 자체가 필요 없고 따라서 라이선스 문제도 없다.
  - 사고 추정 건수를 리포트 프론트매터에서 다시 읽어(README 표 생성에 쓰던 헬퍼 재사용) 0건이면 건너뛰고, 있으면 Issue를 연다. 같은 날짜 Issue가 이미 있으면 새로 만들지 않는다. 조회 자체가 실패하면 중복 방지보다 알림 누락 방지를 우선해 그냥 새로 만든다.
  - Teams 웹훅 경로와는 완전히 독립적이다. 어느 한쪽만 설정돼 있어도 동작한다.
  - 실제 레포에 Issue를 만들어 보고, 재실행 시 중복이 안 생기는 것과 테스트 Issue 정리까지 확인했다.

## 정리

이 파이프라인을 만들면서 계속 되돌아온 원칙은 **"조용한 실패를 잡는 도구가 스스로 조용하면 안 된다"**였다. design과 sds를 감시에서 뺄 때 제외 사실을 콘솔·메타 파일·리포트 세 곳에 남긴 게 그 예다. 제외를 조용히 하면 리포트를 보는 사람은 그 화면들이 멀쩡하다고 읽는다. 같은 이유로 귀속 후보가 여럿이면 여럿 그대로 보고하고 하나로 단정하지 않는다.

**기존 정의를 재사용한 게 이 도구의 뼈대**였다. 라우트 목록을 새로 쓰지 않고 기존 캡처 하네스의 JSON을 읽기 전용 정본으로 삼았고, 대기 판정도 이미 있던 Readiness v2를 그대로 썼고, `.env` 로딩도 다른 곳에서 검증된 로더를 가져다 썼다. 감시 대상 목록이 두 벌로 갈라지면 그 갈라짐 자체가 새로운 누락을 만든다. 누락을 잡으려는 도구가 누락의 원인이 되면 앞뒤가 안 맞는다.

**오탐 하나가 도구 전체를 죽인다**는 것도 몇 번 확인했다. dist-lib 재빌드로 REMOVED가 11건 한꺼번에 터진 사고가 있었고, 그게 캡처 시점 dev 오버레이 끄기와 라이브러리 지문 기록이라는 두 장치를 만든 이유다. 그다음엔 감시하지도 않는 번들의 재빌드 경고가 노이즈로 남아 그것도 걷어냈다. 매일 밤 도는 도구는 오탐이 며칠만 이어져도 아무도 안 보게 된다.

리포트를 **사람용과 기계용으로 동시에 만든 것**도 이번의 선택이다. 본문은 완결된 문장으로 읽히게 하고, 같은 내용을 YAML 프론트매터에 구조로 남긴다. 하루치 리포트만 보면 프론트매터는 군더더기지만, 한 달치가 쌓이면 "이 요소는 자주 사라진다", "이 커밋 패턴이 자주 걸린다" 같은 관계를 그래프로 엮을 수 있다. 그래서 심각도 분류를 넣고, 커밋을 정규화하고, 정보 가치가 낮은 익명 ADDED는 개수만 남기는 식으로 스키마를 한 번 더 다듬었다.

마지막으로 알림 경로에서 배운 게 있다. Power Automate HTTP 트리거가 Premium 라이선스 벽에 막혔을 때, 그 벽을 넘으려 하는 대신 **이미 무료로 열려 있는 다른 길**(GitHub 공식 Teams 앱의 레포 구독)을 썼다. 결과적으로 Issue만 열면 알림이 따라오는 구조가 되어 우리 쪽 코드는 오히려 줄었다.
