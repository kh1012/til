# 검증 3단계(pnpm ui:quality)가 품질 원장 전체를 재기록해서 공유 워크트리에서 다른 세션 커밋을 오염시킨 문제

> maxys_proto에서 검증 레벨 3(`pnpm ui:quality`)을 돌리면 `registry/quality/*.json` 품질 원장 전체가 재기록되는데, 이 워크트리를 여러 세션이 동시에 공유하다 보니 한 세션이 무심코 레벨 3을 고르면 114개 이상의 무관한 파일이 로컬에 변경되어 다른 세션의 커밋에 섞여 들어갈 위험이 있었다. 해결은 서버 쪽 API 검증 경로는 그대로 두고, 작성기(에디터) UI 메뉴에서만 레벨 3 선택을 막는 방어적 UX였다.

## 배경

한 세션이 파일 첨부 리팩터링 작업을 시작하면서 워킹 트리 상태를 확인하다가, 직전 세션(1분 전, 18:14:19 커밋)이 남긴 변경을 발견했다. 커밋 메시지는 "검증 3단계를 작성기에서 못 고르게 막는다"였고, `verify-gate.ts`, `RunSettingsMenu.items.ts`, `run-settings.ts` 세 파일만 건드린 작은 커밋이었다. 왜 갑자기 검증 단계 하나를 UI에서 막아야 했는지가 궁금해서 원인을 추적했다.

## 핵심 내용

**원인은 검증 3단계가 "검증"이 아니라 "재기록"이라는 점이었다.** `pnpm ui:quality`는 실행할 때마다 `registry/quality/*.json` 품질 원장 전체를 처음부터 다시 써낸다. 문제는 이 저장소가 여러 Claude 세션이 동시에 작업하는 공유 워크트리라는 것 — 한 세션이 검증 3단계를 실행하면 자기 작업과 무관한 114개 이상의 로컬 파일이 변경되고, 이 상태에서 다른 세션이 커밋을 만들면 자기가 건드리지도 않은 원장 재기록분까지 같이 딸려 들어갈 수 있었다.

**고친 방식은 "막되, 완전히 막지는 않는다"였다.** 서버 쪽 `verify-gate.ts`의 검증 로직 자체는 건드리지 않아서, API로 직접 레벨 3을 요청하면 여전히 동작한다. 대신 `RunSettingsMenu.items.ts`에서 메뉴 항목을 비활성화하고 "원장 재기록"이라는 이유를 배지로 보여주는 방식으로, 작성기 UI에서 무심코 클릭해 사고를 내는 경로만 막았다. `run-settings.ts`에는 `onSelect` 콜백 가드가 추가됐다. 즉 실수로 트리거되는 경로는 UI 레벨에서 차단하고, 의도적으로 필요한 경우(API 직접 호출)의 능력은 유지하는 절충이었다.

**이 발견 자체도 "혼란의 원인을 추적했더니 이미 고쳐져 있더라"는 케이스였다.** 새 세션이 시작되자마자 워킹 트리에 낯선 변경이 없는지, 세 파일이 커밋된 baseline인지 git 상태로 먼저 확인하고 나서야 안심하고 자기 작업(파일 첨부 리팩터링)을 이어갈 수 있었다 — 공유 워크트리에서는 "내가 안 건드린 변경이 보인다"가 버그가 아니라 다른 세션의 흔적일 수 있다는 걸 매번 구분해야 한다.

## 정리

빌드/검증 스크립트가 "실행해도 아무것도 안 바뀐다"는 멱등성을 암묵적으로 가정하고 여러 세션·CI가 같은 워크트리를 공유하면, 그 스크립트가 실제로는 상태 파일 전체를 재기록하는 순간 조용히 폭발 반경이 커진다. 이럴 때 "검증 로직 자체를 고치는" 대신 "위험한 트리거 경로만 UI에서 막고 백엔드 능력은 유지"하는 방어적 UX는, 근본 원인(원장이 매번 통째로 재기록되는 설계)을 바로 손대기 어려운 상황에서 쓸 수 있는 실용적인 완화책이다. 그리고 공유 워크트리에서 작업을 시작할 때는 낯선 diff를 보면 먼저 "이게 방금 커밋된 다른 세션의 baseline인가"부터 git log/status로 확인하는 습관이 필요하다.
