# 안 보이던 것을 보이게

> 저녁에 한 세 건은 화면 모양이 아니라 정보에 관한 것이었다. 이 컴포넌트가 실제로 어디서 쓰이는지, 지금 몇 개를 골랐는지, 이 기록을 누가 남겼는지. 셋 다 원래는 알 방법이 없거나 unknown으로 뭉개져 있던 값이다.

## 배경

하네스 상세 페이지에는 "쓰이는 곳" 행이 있다. 그런데 그 값은 `composedOf`의 역방향, 즉 다른 레지스트리 컴포넌트가 이 컴포넌트를 조합해 쓰는 경우만 추적하고 있었다. 실제로 사람이 궁금한 건 그것 말고 두 가지가 더 있다. 페이지 플레이그라운드에 이 컴포넌트를 배치했는지, 그리고 모노레포 `apps/` 아래 진짜 제품 코드에서 import하고 있는지. 둘 다 정적 레지스트리만으로는 계산이 안 되니 아예 안 잡히고 있었다.

기록의 주인 문제도 있었다. 히스토리 타임라인의 actor나 updatedBy가 가끔 "unknown"으로 찍혔다. `computeDecidedBy`가 서버 부팅 시 1회 `git config user.name`을 읽고, 실패하면 리터럴 `"unknown"`을 상수로 만들어 모든 쓰기 핸들러에 넘긴 채 화면이 그걸 그대로 보여주고 있었다.

## 핵심 내용

### 개별 작업 기록 (시간순)

- 컴포넌트 지목 팔레트 보내기 버튼 hover + 지목 개수 뱃지
  - `search-palette-row.tsx`의 활성 행 "보내기"(↑) 버튼이 `transition-opacity hover:opacity-90`만 걸고 있었다. 90%면 사실상 원본과 구분이 안 돼 hover가 거의 안 보인다. Button primary variant 관례인 `hover:bg-st-primary/80`으로 통일하고 press 클래스를 더했다. 공유 컴포넌트라 컴포저와 즉시 실행 레퍼런스 피커 양쪽에 동시에 적용된다.
  - 컴포저(`PageFeedbackComposer`)의 컴포넌트 지목 팔레트는 기존 `footerHints`(선택/이동/닫기) 슬롯 맨 앞에 지목 개수를 뱃지로 얹었다. 여러 개를 이어서 지목하는 동안 몇 개 골랐는지 보이는 자리가 없었다. 새 UI를 만드는 대신 이미 있던 힌트 슬롯을 쓴 게 포인트다.

- 상세 페이지 "쓰이는 곳"에 페이지 배치·모노레포 코드 사용처 추가
  - 새 엔드포인트 `GET /api/entry/<name>/usages`(`vite-harness-api-usages.ts`)를 두고 두 갈래를 보강했다.
  - 첫째, `pages/*.json`의 content 트리를 재귀 순회해 `type === 엔트리 name`인 노드가 있는 페이지를 찾는다. page-create GUIDE가 "레지스트리 컴포넌트는 type에 엔트리 name을 쓴다"는 규칙을 이미 못 박아 뒀기 때문에 트리 순회만으로 정확히 잡힌다.
  - 둘째, `apps/` 아래를 rg로 grep해 실제 코드 사용처를 찾는다. 여긴 규칙이 아니라 실제 소스라 정적 분석 대신 텍스트 검색을 택했다.
  - `DetailRoute`가 이걸 fetch해 `PropsPanel`의 "쓰이는 곳" 행에 컴포넌트 링크, 페이지 링크, 코드 상대경로(모노스페이스)를 함께 나열한다. 실패해도 조용히 무시되는 보강 정보라 상세 페이지 자체는 절대 안 깨진다.

- 첫 방문 이름 입력 + git 실패 시 localStorage 폴백
  - 먼저 범위를 갈랐다. "생성자"(`creatorOf`)는 오프라인 배치 스크립트 `resolve-created-by.mjs`가 채우는 완전히 별개 값이라 이 문제와 무관하고, 이번엔 안 건드렸다.
  - 클라이언트는 첫 방문 시 `UserNameModal`로 이름을 받아 localStorage에 저장한다(`user-identity.ts`, 기존 `recents.ts`와 같은 패턴). `user-fetch-interceptor.ts`가 `bridge-fetch-interceptor.ts`와 같은 스타일로 모든 `/api/*` 요청에 `x-harness-user` 헤더를 실어 보낸다. 호출부 13곳을 개별 수정할 필요가 없어진다.
  - 헤더값은 `encodeURIComponent`로 감싼다. 처음엔 raw 문자열을 그대로 실었는데 한글 이름에서 `Headers.set: non ISO-8859-1 code point` 예외가 났다. 브라우저 테스트로 잡아냈다.
  - 서버는 `lib/actor.ts`에 `resolveActor(decidedBy, req)`를 두고, `decidedBy === "unknown"`일 때만 그 헤더를 `decodeURIComponent`해 대신 쓴다. git이 정상이면 헤더 자체를 안 본다.
  - actor/updatedBy를 쓰던 6개 파일 8곳을 이 헬퍼 호출로 치환했다. 전부 이미 `req`를 받고 있어서 시그니처 변경 없이 기계적으로 끝났다.

## 정리

"쓰이는 곳"을 고치면서 확인한 건, **정적 구조가 답할 수 있는 질문과 없는 질문을 먼저 갈라야 한다**는 것이었다. 레지스트리의 `composedOf`는 선언이라 역방향 조회가 공짜지만, 페이지 배치와 실제 코드 import는 선언이 아니라 사실이다. 사실을 알려면 데이터를 실제로 뒤져야 하고, 그건 서버가 파일시스템을 훑는 일이라 클라이언트 렌더 경로에 넣을 수 없다. 그래서 별도 엔드포인트로 뺐고, 상세 페이지 본체와 완전히 분리된 비동기 보강으로 붙였다. 실패해도 페이지가 안 깨지는 건 부수효과가 아니라 이 구조에서 자연스럽게 나오는 성질이다.

같은 "찾기"인데 두 갈래에 서로 다른 방법을 쓴 것도 의도적이다. 페이지 배치는 `type === name`이라는 GUIDE 규칙이 있으니 트리 순회로 정확히 잡을 수 있고, 코드 사용처는 그런 규칙이 없으니 grep이 오히려 정직하다. **규칙이 있는 곳에는 규칙을 쓰고, 없는 곳에 규칙을 발명하지 않는 것**이 나중에 틀려도 덜 아프다.

이름 문제에서 가장 오래 기억할 건 **`"unknown"` 리터럴이 코드를 조용히 오염시킨 방식**이다. git config를 못 읽었을 때 실패를 실패로 표현하지 않고 사람 이름처럼 생긴 문자열로 바꿔 상수에 담아 버리면, 그 값이 8개 호출 지점을 지나 히스토리에 저장되고 화면에 렌더링될 때까지 아무도 그게 "값 없음"이라는 걸 모른다. 이번 수정도 결국 `decidedBy === "unknown"`을 다시 비교해서 원래 의미를 복원하는 모양새가 됐다. 애초에 null이나 명시적 실패 타입이었다면 이런 문자열 비교는 필요 없었을 것이다.

**횡단 관심사는 호출부가 아니라 경계에서 처리한다**는 것도 다시 확인했다. 헤더를 13개 fetch 호출부에 하나씩 넣는 방법과 인터셉터 하나를 까는 방법은 처음 작업량이 크게 다르지 않지만, 새 API를 추가할 때마다 빠뜨리는지 아닌지가 갈린다. 레포에 이미 `bridge-fetch-interceptor.ts`라는 같은 모양의 선례가 있었던 게 결정을 빠르게 만들어 줬다.

그리고 한글 이름 헤더 예외는 브라우저로 실제 입력해 보기 전엔 절대 안 나왔을 종류의 버그다. HTTP 헤더가 ISO-8859-1만 받는다는 건 아는 사실인데, 사용자 입력이 그 통로를 지난다는 걸 코드를 쓰는 순간엔 연결 짓지 못했다. **경계를 넘는 값에는 그 경계의 인코딩 제약이 붙는다**는 걸 사람 이름 같은 평범한 문자열에서 놓치기 쉽다.

세 건을 관통하는 건 결국 같은 형태다. 정보가 없었던 게 아니라 어딘가에 있었는데 화면까지 오는 통로가 없었다. 페이지 JSON에도 apps 소스에도 사용처는 이미 있었고, 사용자는 자기 이름을 알고 있었고, 지목 개수는 상태에 들어 있었다. 통로를 하나씩 뚫는 일이었다.
