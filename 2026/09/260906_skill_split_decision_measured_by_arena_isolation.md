# atelier-component-process·atelier-page-process 스킬을 생성/수정으로 쪼갤지 말지를 아레나 격리 실행으로 실측해 분리하지 않기로 결정한 사례

> 컴포넌트·페이지 스킬이 생성과 수정(분할 포함)을 한 스킬 안에 담고 있어 분리가 최적인지 판단이 필요했다. 감으로 정하지 않고 격리 아레나에서 즉시실행 일곱 종을 실제로 돌려 각 경로가 실제로 여는 문서 바이트를 재고, 그 수치로 "분리하지 않는다"를 결정했다.

## 배경

atelier 워크벤치의 컴포넌트·페이지 스킬(`atelier-component-process`, `atelier-page-process`)은 생성·수정·분할 절차를 모두 한 스킬 파일 안에 담고 있었다. 스킬 설명이 컨텍스트에 상시 상주하는 구조라, 절차가 하나로 뭉쳐 있으면 실제로는 수정만 하는 요청에서도 생성 관련 서술까지 다 읽게 되는 게 아닌지가 의심스러웠다. 분리하면 최적화가 되는지, 아니면 오히려 비용만 늘리는지를 판단해야 했다.

## 핵심 내용

**감으로 판단하지 않고 격리 아레나를 띄워 실측했다.** 공유 워크트리를 건드리지 않는 별도 스택(9151~9153)을 세우고, 컴포넌트 생성 1·2단계, 컴포넌트 수정, 컴포넌트 분할, 컴포넌트 개선, 페이지 생성·수정까지 즉시실행 일곱 종을 전부 돌려 각 경로가 실제로 연 문서와 바이트 수를 쟀다.

| 즉시실행 | 실제로 연 문서 | 바이트 |
| --- | --- | --- |
| 컴포넌트 생성 1단계 | GUIDE + search.md | 24,670 |
| 컴포넌트 생성 2단계 | GUIDE + search.md + create.md | 42,580 |
| 컴포넌트 수정 | GUIDE + modify.md | 26,801 |
| 컴포넌트 분할 | GUIDE + create.md + modify.md + examples.md | 49,520 |
| 컴포넌트 개선 | GUIDE + modify.md + design-system.md | 34,135 |
| 페이지 생성·수정 | GUIDE(page) + rules.md | 23,491 |

**분리하지 않기로 한 근거는 넷이다.**

- 경로 분기가 이미 파일 단위로 존재한다. 생성은 `create.md`, 수정은 `modify.md`만 연다. 스킬 이름을 쪼개도 이 선택 자체는 그대로다.
- GUIDE의 공유분이 압도적이다. 컴포넌트 GUIDE 열아홉 절 중 생성 전용은 두 절, 650바이트뿐이고 나머지는 자리 확인·진행 방식·검증 게이트·HITL 형식·절대 규칙으로 모든 경로가 함께 쓴다. 쪼개면 이 공유분이 두 벌로 복제되어 총량이 늘고, 두 사본이 갈라져도 알아챌 방법이 없다.
- 분할 절차는 원래 두 경로를 다 쓴다. 쪼개진 조각은 생성 절차로 만들고 부모는 수정 절차로 되세운다. 스킬을 나누면 이 하나의 절차를 위해 두 스킬을 함께 열어야 한다.
- 스킬이 늘면 상시 상주 비용도 함께 는다. 설명이 둘에서 넷이 되고, 설치 스크립트·프롬프트·화면 문안·시험 열세 자리를 같이 갈아야 한다.

대신 값이 있는 손질은 스킬 분리가 아니라 프롬프트 쪽에서 나왔다. 분할 프롬프트만 스킬 이름을 부르고 파일을 안 짚어서, 그 실행이 도구 호출 예순다섯 번으로 가장 많았고 문서를 스스로 뒤져 49KB를 읽었다. 수정 프롬프트처럼 `create.md`·`modify.md`를 프롬프트에 직접 적으면 이 탐색이 준다.

**결정 뒤에 격리 사본에서 Playwright로 일곱 경로 전부를 검증했다.** 생성·수정·분할·개선·페이지 생성·페이지 수정·재사용 결정(HITL) 모두 정상 동작을 확인했고, 이 과정에서 스킬 분리와 무관한 결함 셋을 별도로 찾았다(컴포넌트 프리뷰 264개 오류, 승격 화면 연결 끊김, 개선 프롬프트 빈 제출 처리 누락) — 모두 요청 범위 밖이라 손대지 않고 기록만 남겼다.

## 정리

스킬을 쪼갤지 말지 같은 구조 판단은 "읽는 양이 줄 것 같다"는 직관이 아니라, 격리 환경에서 실제 경로를 다 돌려 실제로 열리는 문서와 바이트를 재는 쪽이 답을 준다. 이번 경우 조건부 읽기가 이미 파일 단위로 되어 있어서 스킬 단위 분리는 이득 없이 공유 문서만 복제시켰고, 진짜 비효율은 스킬 경계가 아니라 프롬프트가 파일을 안 짚어 스스로 탐색하게 만든 지점에 있었다. 구조를 바꾸기 전에 그 구조가 실제로 무엇을 읽는지부터 재는 습관이 잘못된 분리를 막았다.
