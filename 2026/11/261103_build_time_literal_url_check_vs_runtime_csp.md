# 플러그인 코드의 외부 직접 호출을 막을 때, 빌드 타임 정적 검사와 런타임 CSP/세션 필터의 책임을 나눈 사례

> plugin-builder에서 "빌드 때 직접 호출 거절"을 구현하면서, 정적 검사(`direct-call.ts`)는 리터럴 URL만 잡고 변수·문자열 조합 URL은 일부러 통과시켰다. 그 빈틈은 이미 런타임 CSP와 Electron 세션 필터가 막고 있기 때문이다.

## 배경

사용자 플러그인 코드가 `fetch`, `WebSocket`, `axios`, `sendBeacon`, `EventSource`, `XMLHttpRequest`로 외부 주소를 직접 호출하는 걸 막아야 했다. 런타임에는 이미 CSP와 Electron 세션 필터가 이런 호출을 걸러내고 있었는데, 거기에 더해 빌드 타임에도 거절하는 `direct-call.ts` 검사를 추가하는 작업이었다.

## 핵심 내용

**검사 범위를 리터럴 URL로 한정**: `direct-call.ts`는 `src/` 디렉터리를 스캔하면서 `http://`, `https://`, `ws://`, `wss://`로 시작하거나 프로토콜 상대(`//`)로 쓰인 **리터럴 문자열** URL만 잡는다. 변수에 담긴 URL이나 문자열 조합으로 만들어진 URL은 검사 대상에서 뺐다.

**왜 변수·조합 URL을 빼도 되는가**: 정적 분석으로 변수 값이나 문자열 조합 결과를 추적하려면 분석기가 훨씬 복잡해지고 오탐도 늘어난다. 대신 그 경로로 나가는 호출은 런타임의 CSP와 Electron 세션 필터가 이미 막는다. 빌드 타임 검사는 "쉽게 잡을 수 있는 걸 빨리, 개발자 눈에 보이는 에러로" 잡고, 나머지는 런타임 방어선에 맡기는 역할 분담이다.

**오탐 방지 처리**: `blankScriptComments()`로 주석(`//`, `/* */`)을 줄 위치는 유지한 채 비워서, 주석 처리된 코드의 URL을 에러로 잘못 잡지 않게 했다. 검사 대상은 `.ts`, `.tsx`, `.js`, `.jsx`, `.mjs`, `.cjs`, `.mts`, `.cts`이고 `node_modules`, 관리 폴더, 심볼릭 링크, 점 폴더, 2MB 넘는 파일, 5000개 넘는 파일은 스캔에서 뺐다.

**에러 출력도 보수적으로**: 에러는 `파일:줄 핸들러 origin` 형식으로 최대 50줄까지만 보여주고, 그 이상은 개수만 요약한다. URL의 경로·쿼리스트링은 빌드 로그에 남기지 않아 키 유출을 막았다.

## 정리

같은 위협(플러그인의 외부 직접 호출)을 막는 방어선이 두 겹일 때, 두 겹 모두 완전함을 추구할 필요는 없다. 빌드 타임 검사는 "리터럴 URL만 잡는 보수적인 정적 분석"으로 범위를 좁히고, 그 빈틈은 이미 런타임 CSP/세션 필터가 메우고 있다는 전제 위에 설계했다. 정적 분석을 어디까지 욕심낼지 정할 때, 다른 레이어가 이미 커버하는 범위를 파악하고 거기에 겹치지 않는 선에서 단순하게 유지하는 쪽이 유지보수하기 쉽다.
