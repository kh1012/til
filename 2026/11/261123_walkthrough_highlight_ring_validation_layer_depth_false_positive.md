# 워크스루 하이라이트 링 지오메트리 검증이 레이어 깊이를 안 따져서 생긴 거짓 양성 고침

> Builder Docs의 인터랙티브 워크스루(커서가 움직이며 UI를 짚어주는 애니메이션 가이드)를 검증하는 스크립트가, 강조 테두리(하이라이트 링)가 대상 바깥 텍스트와 겹친다는 거짓 양성을 12건 냈다. 원인은 겹침 판정이 2D 사각형 교차만 보고 그 텍스트가 대상보다 아래 레이어에 있어서 실제로는 대상에 가려 보이지 않는다는 사실을 무시한 것이었다. 레이어 깊이를 비교에 넣어 고쳤다.

## 배경

Builder Docs에 신규 플러그인/커넥터 설정 흐름을 보여주는 워크스루를 JSON으로 선언하고, 커서 이동·클릭·강조를 재생하는 플레이어 컴포넌트를 붙이는 작업을 했다. 이 워크스루가 실제 앱 화면과 어긋나지 않는지(글자가 넘치거나, 잘리거나, 대상 강조 링이 엉뚱한 요소를 가리키지 않는지) 사람이 매번 눈으로 확인할 수 없으니 `walk-check.mjs`라는 자동 검증 스크립트를 만들었다. CDP(Chrome DevTools Protocol)로 실행 중인 dev 앱에 붙어 각 워크스루 단계의 화면을 고정시키고, DOM에서 텍스트 bounding box·레이어(`base`/`dialog`/`popover`/`menu`/`toast`)·계산된 스타일을 뽑아 `walk-judge.mjs`의 5가지 규칙(overflow, clip, overlap, cover, target highlight)으로 판정한다.

첫 실행에서 32개 프레임 중 104건이 걸렸는데, 그중 대상 강조(target highlight) 링 문제가 12건이었다. 하나씩 스크린샷으로 확인해보니 실제로는 아무 문제가 없었다 — 강조 링이 가리키는 버튼 밑에 깔린 텍스트가 사각형 좌표상으로만 링과 겹쳤을 뿐, 그 버튼 자체에 완전히 덮여 화면에는 보이지 않는 상태였다.

## 핵심 내용

**검증 로직의 전제가 틀렸다**: `walk-judge.mjs`는 하이라이트 링의 bounding box와 "대상이 아닌 다른 텍스트"의 bounding box가 겹치면 바로 문제로 기록했다. 이 비교는 평면 좌표만 보고, 그 텍스트가 어떤 레이어에 있는지는 보지 않았다.

**실제로는 레이어가 다르면 겹침이 의미 없다**: 대상 버튼보다 아래 레이어(`base`)에 있는 텍스트는, 설령 2D 좌표상 버튼과 겹치더라도 버튼에 가려 화면에 안 보인다. 사람이 스크린샷을 봐도 문제가 없는 이유다. 반대로 대상과 같거나 위 레이어에 있는 텍스트가 링과 겹치면 그건 실제로 화면에 같이 보이는 충돌이라 거짓 양성이 아니다.

**고친 방법은 "대상의 레이어보다 아래면 제외"**: `collect()` 단계에서 각 요소에 레이어 깊이 속성을 추가해 target highlight 판정에 넘기고, `walk-judge.mjs`에서 겹치는 텍스트의 레이어가 대상의 레이어보다 아래면 그 겹침을 건너뛰도록 했다. 디버깅용으로 프레임별 원본 지오메트리 측정치를 JSON으로 뽑는 `--raw` 플래그도 같이 추가했다 — 좌표만으로는 레이어 누락을 알아채기 어려워서다.

**효과는 수치로 확인**: 대상 강조 관련 거짓 양성이 12건에서 0건으로, 전체 발견 건수가 104건에서 73건(28% 감소)으로 줄었다. 나머지 73건은 대부분 오버레이(dialog/popover/toast)가 텍스트를 부분적으로 가리는 것으로, 워크스루 맥락에서는 의도된 동작이라 별도로 다룰 항목이다.

## 정리

화면 요소의 겹침을 bounding box 교차만으로 판정하면, 쌓임 순서(stacking order)상 뒤에 있어서 실제로는 안 보이는 겹침까지 전부 문제로 잡는다. 스크린샷 기반 지오메트리 검증을 짤 때는 좌표 비교에 레이어/z-order를 같이 넣어야 한다 — 2D 좌표계만으로는 "겹쳐 보인다"와 "좌표가 겹친다"를 구분할 수 없다.
