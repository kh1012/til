# 탭마다 여는 스트리밍 연결이 HTTP/1.1 호스트당 6연결 제한에 걸려 커넥션 풀을 고갈시킨 원인과 세 가지 해결 전략

> Plugin Builder에서 편집 탭을 5개 이상 열고 도움말을 동시에 켜면 요청이 멈췄다. 원인은 Chromium의 HTTP/1.1 호스트당 6연결 제한이었다.

## 배경

Plugin Builder 앱에서 편집 탭을 여러 개(5개 이상) 열어 둔 채 도움말(help) 패널을 켜면 추가 요청이 응답을 못 받고 대기 상태에 빠지는 현상이 보고됐다. PF1 조사(이슈 #355)에서 원인을 추적한 결과, 네트워크 레이어의 구조적 제약이 드러났다. 이 조사와 후속 PF2 전략 수립은 `core/pf1/causes-2026-11-07.md`에 정리됐다.

## 핵심 내용

**편집 탭 하나당 스트리밍 연결 하나를 연다**: 각 편집 탭은 `GET /api/agent/stream`(keepalive 스트림)을 하나씩 열고, 도움말 시스템도 별도로 `GET /api/help/stream`을 연다. 탭 수가 늘수록 열린 상태를 유지하는 연결 수도 그만큼 늘어난다.

**Chromium은 origin당 HTTP/1.1 동시 연결을 6개로 제한한다**: 이 숫자는 Plugin Builder가 바꿀 수 있는 값이 아니라 브라우저가 프로토콜 레벨에서 강제하는 상한이다. 편집 탭 5개 + 도움말 스트림 1개만으로 이미 6개 슬롯이 전부 소진된다. 이 상태에서 새로 생기는 요청(새 탭 열기, 다른 API 호출 등)은 기존 연결 중 하나가 끝날 때까지 큐에서 대기한다.

**같은 shell 출처에서 보낸 화면 요청으로도 재현된다**: 특정 UI 조작 없이도 하나의 shell에서 연속으로 화면 요청을 보내는 것만으로 같은 병목이 재현됐다. 즉 문제는 특정 상호작용이 아니라 "동시에 열려 있는 keepalive 스트림 개수" 자체에 있다.

**해결 방향은 하나가 아니라 세 갈래로 잡았다**:
- 탭마다 별도 연결을 여는 대신, 창(window) 하나당 진행 상태 스트림을 하나만 두고 shell 레이어에서 유닛(edit/theme/help)별로 멀티플렉싱한다.
- 편집 탭 수 자체를 최대 4개로 제한하고, 한도를 넘으면 가장 오래 보지 않은 탭을 LRU로 내보낸다.
- 탭 6~8개 + 테마 + 도움말을 동시에 띄우는 e2e 테스트를 만들어 회귀를 막는다.

세 전략은 서로 배타적이지 않고 비용/효과를 비교해 선택하기 위해 병렬로 계획됐다.

## 정리

브라우저가 강제하는 프로토콜 레벨 제한(origin당 연결 수)은 애플리케이션 코드를 아무리 고쳐도 피해 갈 수 없는 상한이다. "요청이 느려진다"를 서버 처리 시간이나 네트워크 지연으로 먼저 의심하기 쉽지만, 동시에 열려 있는 keepalive 연결 개수부터 세어 보는 편이 원인 분리가 빠르다. 근본 해결은 연결 수 자체를 줄이는 것(스트림 공유)과 연결을 만드는 소스 수를 줄이는 것(탭 제한) 두 방향으로 갈리며, 둘 다 회귀 테스트 없이는 효과를 검증하기 어렵다.
