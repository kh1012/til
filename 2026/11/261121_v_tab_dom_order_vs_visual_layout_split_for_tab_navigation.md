# Tab 키 포커스 순서가 피드 글 개수에 비례해 느는 문제를 DOM 순서와 시각 레이아웃 분리로 고침

> 모임(그룹) 화면에서 Tab 키로 하단 입력창(글 남기기)에 닿으려면 글이 60개 있을 때 181번을 눌러야 했다. 각 게시물의 좋아요·답글·반응추가 버튼이 DOM 순서상 입력창보다 먼저 있어서, Tab이 게시물 수만큼 그 버튼들을 다 돌고 나서야 입력창에 도달했다. DOM 순서만 앞으로 당기고 화면에 보이는 자리는 그대로 두는 방식으로 고쳤다.

## 배경

CM2(Community Manager 2) 화면 시나리오 매트릭스에서 키보드 접근성 항목 중 유일하게 "어긋남"으로 남아있던 게 V-TAB이었다. 60개 글이 있는 모임에서 Tab으로 하단 입력창에 닿는 데 181번, 우측 메뉴(RNB)에 닿는 데 187번이 필요했다. 접근성 기준은 30번 이내였다.

## 핵심 내용

**원인은 DOM 순서가 피드 글 개수에 선형으로 비례했다는 것**: 화면에는 입력창이 하단에, 우측 메뉴가 옆에 고정되어 보이지만, DOM에는 피드의 게시물들이 먼저 나열되고 입력창·메뉴가 그 뒤에 있었다. 게시물마다 좋아요/답글/반응추가 버튼이 있으니 Tab이 그 버튼들을 글 수만큼 반복해서 돈 다음에야 입력창에 도달했다.

**해결은 DOM 순서와 시각 순서를 분리하는 것**: 화면 자리는 그대로 두고 DOM에서만 입력창(dock)·우측메뉴(rail)를 피드 본문(body)보다 앞에 둔다 — head → dock → rail → body 순. Tab 순서는 DOM 순서를 따르므로 이렇게 하면 Tab이 입력창·메뉴를 먼저 지나가고, 그 다음에 게시물 버튼들로 들어간다. 대안으로 단축키(N)를 거는 방법도 검토했으나 채택하지 않았다 — DOM 순서 자체를 고치는 쪽이 특수 키 학습 없이도 동작해서다.

**시각 레이아웃은 CSS로 복원**: `community.css`에서 grid 책임을 `.cm-group.is-wide`에서 `.cm-gcol`로 옮기고, body를 grid-area 1/1, dock을 2/1(본문 열 아래), rail을 1/2/-1(우측 전체 높이)에 배치했다. dock이 없는 탭(구성원, 소개)에서는 `:has(> .cm-dock-wrap)` 선택자로 두 번째 grid row를 조건부로만 추가했다. 좁은 화면에서는 flexbox `order: 1`로 dock을 하단에 배치했다.

**레이아웃 구조는 컴포넌트로 고정**: `group-view.tsx`에 흩어져 있던 JSX 조건문을 `GroupFrame` 컴포넌트로 뽑아 head/dock/rail/body 순서를 강제한다. 없는 섹션은 null로 렌더해 DOM 순서를 유지한다 — 이렇게 하면 화면 너비가 바뀔 때 컴포넌트가 리마운트되면서 사용자가 쓰던 글(draft)이 날아가는 문제도 같이 막힌다.

**검증은 수치와 픽셀 diff 둘 다로**: Tab으로 입력창 도달 117→1번, 우측메뉴 120→3번으로 줄었다. 전후 스크린샷 픽셀 diff로 시각 레이아웃 변화가 rail/feed 영역의 그리드 트랙 이동에 따른 미세한 리플로우(채널 차이 대부분 8 이하)뿐이고 구조적 깨짐은 없음을 확인했다. CM2 시나리오 매트릭스 e2e도 "어긋남"에서 "통과"로 바뀌었다.

## 정리

Tab 순서 문제를 CSS만으로 풀려고 하면 한계가 있다 — CSS는 시각 위치를 바꿀 뿐 DOM 순회 순서(=Tab 순서)는 바꾸지 못한다. 반복되는 하위 요소(게시물 버튼 등)가 포커스 가능한 요소를 다수 포함하고, 그 개수가 늘어날수록 전역 내비게이션(입력창, 메뉴)에 닿는 Tab 횟수가 선형으로 늘어나는 구조라면, DOM 순서 자체를 재배치하고 시각 위치는 grid-area·flexbox order로 되돌리는 분리가 필요하다.
