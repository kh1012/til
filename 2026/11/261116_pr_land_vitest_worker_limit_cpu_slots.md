# pr-land 테스트 병목 원인을 lock 대기가 아니라 vitest worker 무제한 생성으로 측정해 CPU 슬롯 제한으로 고친 결정

> pr-land는 머지 직전 구간만 lock으로 직렬화하고 테스트 구간은 lock 없이 동시에 돈다. 여러 세션이 겹쳐 돌 때 pr-land가 느려진다는 체감을 두고 "동시에 도는 세션 수를 줄이면 빨라지는가"를 물었는데, 4일치 로그 225개를 측정해 보니 lock 대기 시간은 거의 0이었고 실제 병목은 테스트 구간 자체였다. vitest가 CPU 코어 수만큼 worker를 제한 없이 띄워서, pr-land 인스턴스 여러 개가 겹치면 12코어 기기에 vitest worker 90개가 동시에 돌았다. 파일당 테스트 시간이 가벼운 부하에서 0.13초, 무거운 부하에서 5.92초로 45배 느려졌다. 해결은 lock을 더 걸어 직렬화하는 쪽이 아니라 vitest `maxWorkers`를 CPU 코어 수 / 슬롯 수로 제한하는 CPU 슬롯 시스템(PL3-1)이었다.

## 배경

plugin-builder 저장소에서 pr-land(PR을 자동으로 머지하는 스크립트)가 여러 세션이 동시에 돌 때 느려진다는 문제가 있었다. "함께 돌리는 세션 수를 늘리면 빨라지는가, 느려지는가"라는 질문에서 조사가 시작됐다. 직관적으로는 pr-land의 lock(머지 직전 구간을 한 번에 하나만 돌게 막는 장치)이 병목이라고 짐작하기 쉬웠다 — 여러 인스턴스가 lock을 기다리며 줄 서 있을 거라는 그림이다. 2026-11-13~16 나흘치 pr-land 로그 225개와 테스트 실행 로그 243개를 직접 분석해 이 짐작을 검증했다.

## 핵심 내용

**lock 대기는 문제가 아니었다**: pr-land의 lock 큐는 FIFO로 잘 동작했고, 대기 시간은 부하가 아주 심한 날을 빼면 거의 0초였다. lock이 걸리는 구간(머지 + push + PR 생성)은 중앙값 131초로 오히려 짧았다. 반면 lock 없이 여러 인스턴스가 동시에 도는 테스트 구간은 중앙값 391초로 3배 더 걸렸다. 느려지는 쪽은 lock으로 막아 둔 구간이 아니라, 막아 두지 않아서 자유롭게 겹칠 수 있는 구간이었다.

**원인은 vitest worker 수에 상한이 없었던 것**: `vitest.config.ts`에 `maxWorkers` 설정이 없어서 vitest는 기본값대로 논리 코어 수(12코어 기기에서 24)만큼 worker를 띄웠다. pr-land 인스턴스 3개가 겹치자 실제로는 vitest worker 90개가 동시에 돌았다 — 코어당 7.5개. 거기에 각 워크트리가 독립된 pnpm store(813MB)와 node_modules(735MB)를 들고 있어서, 워크트리 22개가 디스크 I/O까지 경합했다. 이 상태에서 시스템 load average가 93.5까지 올라갔고 스왑 17GB를 다 썼다.

**측정값이 상한값을 정했다**: 파일당 테스트 시간을 부하 구간별로 나눠 보니 가벼운 부하(파일당 0.15초 미만) 0.13초, 무거운 부하(0.6초 초과) 5.92초로 45배 차이가 났다. 동시 세션 수별 처리량(tests/min)은 2~4개 구간에서 338개/분으로 가장 높았고, 6~9개로 늘리면 171개/분으로 오히려 떨어졌다. 이 2~4라는 숫자가 그대로 `CPU_SLOTS` 기본값 3이 됐다 — 추측이 아니라 99회 실행 로그에서 직접 뽑은 값이다.

**해결은 직렬화가 아니라 상한이었다**: PL3-1 구현은 `CPU_SLOTS`(기본 3, `TEST_CPU_SLOTS`로 조정 가능)를 두고 `vitest --maxWorkers = 사용 가능 코어 수 / CPU_SLOTS`로 계산한다. 테스트를 실행하기 전에 CPU 슬롯을 하나 잠그고, 잠그는 데 걸린 시간을 기록하고, 프로세스 우선순위를 낮춘다(`nice 10`). pr-land의 lock 구간(`TEST_RUN_IN_LOCK=1`)은 이미 한 번에 하나만 돌므로 슬롯을 따로 잠그지 않는다. "동시에 도는 개수를 줄인다"가 아니라 "각 인스턴스가 쓸 수 있는 worker 수 자체를 줄인다"는 접근이다.

## 정리

겹쳐서 느려지는 문제를 보면 lock처럼 눈에 보이는 직렬화 지점을 먼저 의심하게 되는데, 이번엔 그 지점이 오히려 멀쩍이 비켜 있었다. 병목은 "막아 두지 않아서 자유롭게 겹친" 구간, 그리고 그 구간 안에서 하나의 도구(vitest)가 상한 없이 자원을 긁어 쓴 것이었다. 로그에서 부하별 구간을 나눠 처리량 곡선을 그려 보지 않았다면 "세션 몇 개가 적당한가"라는 질문에 숫자로 답할 수 없었을 것이다. 동시성 문제를 다룰 때 "어디를 직렬화할까"보다 먼저 "각 실행 단위가 자원을 얼마나 쓰고 있는가"를 측정하는 쪽이 먼저라는 점을 다시 확인했다.
