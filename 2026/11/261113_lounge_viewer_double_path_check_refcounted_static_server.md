# 외부에서 받은 콘텐츠를 로컬에 캐시해 띄울 때, 경로 검사를 문자열 단계와 resolve 단계 양쪽에 두고 서버를 참조 계수로 관리한 결정

> Plugin Builder에 "오픈 라운지"(OL1) 기능을 넣으면서, 다른 사용자가 올린 플러그인 페이지를 받아 로컬에 캐시하고 격리된 정적 서버로 띄우는 `lounge-views.ts`를 짰다. 받는 파일의 경로를 한 번만 걸러내지 않고 문자열 검사와 resolve 뒤 경계 검사 두 단계로 나눠 둔 점, 같은 항목을 여러 보기가 동시에 열 때 서버를 참조 계수로 관리한 점이 핵심이다.

## 배경

OL1은 플러그인을 처음 만들거나 편집하는 중 3분 이상 기다리는 동안 다른 사용자가 올린 플러그인(게임, SVG 애니메이션)을 보여주는 기능이다. 라운지 서버(`lounge-server/`)에 올라온 항목의 빌드 결과 페이지를 앱 쪽(`lounge-views.ts`)이 받아 와 로컬에 두고, 실행 미리보기와 같은 정적 서버 인프라(`startStaticServer`)로 `127.0.0.1`에 띄운 뒤 그 주소만 webview에 싣는다. 다른 사용자가 만든 파일을 내 디스크에 쓰고 내 프로세스로 서빙하는 경로라서, [[261112_proxy_narrow_image_exception_for_osm_tiles]]에서 다룬 프록시 경계와 같은 축의 문제가 생긴다 — 이번엔 요청을 막는 쪽이 아니라 받은 내용을 어떻게 가둬 두느냐가 쟁점이다.

## 핵심 내용

**경로 검사를 문자열 검사 하나로 끝내지 않는다**: `safePagePath()`가 받는 파일 목록에서 절대 경로·`..`·`.`·역빗금·NUL을 먼저 걸러낸다. 그런데 `fetchPage()` 안에서 실제로 파일을 쓸 때 `resolve(tmp, f.path)`로 만든 최종 경로를 `file.startsWith(resolve(tmp) + sep)`로 다시 확인한다. 문자열 패턴 검사와 resolve 뒤 경계 검사는 서로 다른 것을 잡는다 — 전자는 입력 자체의 생김새를, 후자는 플랫폼의 경로 해석 결과가 실제로 그 폴더 안에 머무는지를 본다. 한쪽만 두면 둘 사이 틈으로 빠져나가는 입력을 놓칠 수 있다는 전제로 이중화한 것.

**받기는 임시 폴더에, 완료 판정은 rename 하나로**: 파일들을 `.page-<pid>-<timestamp>` 임시 폴더에 다 받은 뒤에만 `page/`로 옮긴다(rename). 받는 중 하나라도 실패하면 임시 폴더를 통째로 지우고 `page/`는 생성되지 않는다 — 부분적으로 받은 상태가 "받아 둔 버전"으로 보이는 경우가 없다. 이미 `page/`가 있으면 재수신 자체를 하지 않아, 같은 버전을 두 번 내려받는 일도 없앴다.

**크기·개수 상한을 받기 전에 정한다**: `MAX_BYTES`(50MB), `MAX_FILES`(2,000)를 `fetchPage` 시작 시점에 정하고, 파일 목록은 `slice(0, MAX_FILES)`로 자르고, 받는 도중 합계가 `MAX_BYTES`를 넘으면 즉시 예외로 중단한다. 라운지 항목은 다른 사용자가 올린 콘텐츠이므로 양을 신뢰하지 않는다는 전제가 깔려 있다.

**서버는 항목당 하나, 참조 계수로 관리한다**: 같은 라운지 항목을 실행 탭과 "새 플러그인 만들기" 미리보기가 동시에 열 수 있다. 이때 서버를 두 개 띄우지 않고 `Entry.users` 카운트를 올리고, `close()`가 호출될 때마다 하나씩 내려 0이 되면 그제서야 정적 서버를 닫는다. 받는 중에 같은 id로 또 열리면 `pending` Map에 걸린 진행 중인 Promise를 그대로 기다리게 해(중복 다운로드 방지) 받기 자체도 한 번만 일어나게 했다.

**CSP는 실행 중인 플러그인과 같은 `run` 모드, 바깥 호출 없음**: 띄운 서버의 CSP 정책은 `allowed: [], dev: []`로, 외부 네트워크를 전혀 부르지 않는다. 라운지 콘텐츠는 빌드 실행 미리보기와 같은 신뢰 수준으로 다루되, 그 샌드박스 바깥으로 나가는 길은 열어 두지 않았다.

## 정리

같은 종류의 검사를 한 번만 하고 넘어가지 않고, 입력 문자열 단계와 실제 파일시스템 해석 단계에 따로 둔 것이 이번 결정의 중심이다. [[261112_proxy_narrow_image_exception_for_osm_tiles]]가 "어떤 요청을 통과시킬 것인가"를 축마다 나눠 판단했던 것처럼, 여기서는 "받은 파일이 정말 그 폴더 안에 있는가"를 묻는 지점을 하나 늘려 둔 셈이다. 검사를 이중으로 두는 비용은 코드 몇 줄이지만, 한쪽이 뚫렸을 때 나머지 한 쪽이 남아 있는 구조를 만든다.
