# composer-docs e2e 테스트가 regex를 직접 베껴 쓰다 깨진 걸, 프로덕션 nameNote 함수를 그대로 가져다 쓰도록 고친 결정

> BUILDER-190 기능이 첨부 파일 경로 뒤에 `(원래 이름: 검토.pdf)` 같은 원래 이름 주석을 붙이기 시작하자, composer-docs.spec.ts의 경로 검증 regex(`/a-[0-9a-f]{16}\.pdf$/`)가 그 꼴을 모르고 그대로 깨졌다. 고친 방법은 테스트 쪽 regex를 수동으로 다시 맞추는 게 아니라, 그 주석을 만드는 프로덕션 함수 `nameNote()`를 테스트에서 import해 기대값을 직접 만들도록 바꾸는 것이었다.

## 배경

plugin-builder 저장소에서 "붙인 파일의 원래 이름을 에이전트에 함께 넘긴다"(BUILDER-190, 커밋 5b1b50356)가 머지되면서 `attach-tail.ts`의 `nameNote()` 함수가 첨부 경로 뒤에 ` (원래 이름: ${원래파일명})` 문자열을 붙이기 시작했다. 그런데 composer-docs.spec.ts는 PDF·XLSX·DOCX 세 첨부 파일의 agent 호출 내용을 검증할 때 경로를 `/a-[0-9a-f]{16}\.pdf$/` 같은 정규식으로 끝에서 매칭하고 있었다. 실제로 받은 경로는 끝에 원래 이름 주석이 더 붙어 있어 이 매칭이 깨졌고, main 배포 게이트가 "새 실패 1개가 남아 배포하지 않는다"며 막혔다.

## 핵심 내용

**기능은 맞게 동작했고, 테스트가 그 변경을 따라가지 못했다**: nameNote 주석은 설계대로 붙은 것이었다. 문제는 테스트가 "첨부 경로가 어떻게 끝나야 하는가"를 자기 나름의 regex로 다시 정의해 두고 있었다는 점이다. 기능 쪽 포맷이 바뀔 때마다 테스트의 regex도 사람이 손으로 맞춰 고쳐야 하는 구조였고, 이번처럼 한쪽만 머지되면 바로 깨진다.

**고친 방식은 regex 재작성이 아니라 함수 재사용**: 커밋 8ddff5b4d는 `attach-tail.ts`의 `nameNote`를 테스트 파일에 직접 import해서, 기대 문자열을 `경로 + nameNote("검토.pdf")` 식으로 만들었다. `pathOf` 헬퍼로 경로를 뽑고, 거기에 실제 프로덕션 함수를 그대로 적용해 기대값을 만드는 구조로 바뀌었다. 이러면 nameNote의 포맷이 다음에 또 바뀌어도 테스트는 같은 함수를 호출하므로 자동으로 따라간다.

**깨진 지점은 "포맷을 두 번 정의한 자리"였다**: 첨부 경로 뒤에 붙는 포맷이 프로덕션 코드(`nameNote`)와 테스트(하드코딩 regex)에 각각 따로 존재했다. 포맷이 하나뿐일 때는 둘이 우연히 맞아떨어지지만, 포맷에 변화가 생기는 순간 둘 중 하나만 고쳐지면서 어긋난다. 테스트가 "출력이 이런 꼴이어야 한다"를 독자적으로 재정의하는 대신 "출력을 만드는 함수를 그대로 가져다 쓴다"로 바뀌면 이 어긋남 자체가 구조적으로 없어진다.

## 정리

포맷을 검증하는 테스트에서 기대값을 리터럴 패턴이나 regex로 다시 적어두면, 그 포맷을 만드는 코드와 검증하는 코드가 별도의 소스가 된다. 둘 다 맞게 짜여 있어도 한쪽만 바뀌는 순간 깨지는 결합이다. 가능하면 테스트가 실제 포맷 생성 함수를 import해서 기대값을 만들게 하면, 포맷이 바뀔 때 테스트가 함께 따라가고, 정말 포맷이 깨졌을 때만 실패한다.
