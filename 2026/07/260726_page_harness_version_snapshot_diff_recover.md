# 버전 스냅샷을 실제로 열어보고, 비교하고, 원본을 건드리지 않고 복구한 날

> page-harness의 불변 버전 스냅샷을 read-only로 미리보기하고, 두 버전을 구조 단위로 비교하는 순수 함수 diff를 붙이고, 선택한 버전에서 독립 draft를 만드는 복구 경로를 열었다. 제자리 복원은 안전 조건을 못 갖춰 만들지 않았다.

## 배경

page-harness는 페이지를 저장할 때마다 `pages/.versions/<slug>/<version>.json`에 불변 스냅샷을 남기고 있었다. 그런데 화면에서 그 스냅샷을 실제로 볼 방법이 없었다. 상세 화면에 있던 history 사이드카는 "언제 누가 어느 버전을 만들었나"만 담고 data는 담지 않으므로, 과거 상태가 어땠는지는 파일로만 존재하고 사람 눈에는 보이지 않는 상태였다.

그래서 이날의 목표는 저장만 되고 쓰이지 않던 스냅샷 자산을 실제 도구로 만드는 것이었다. 세 가지가 필요했다. 과거 버전을 그대로 그려보는 것, 두 버전이 무엇이 달라졌는지 아는 것, 마음에 드는 과거 상태로 돌아가는 것.

다만 세 번째, 즉 "돌아간다"를 어떻게 구현할 것인지가 이날의 실질적인 설계 지점이었다. 현재 페이지를 제자리에서 과거로 되돌리는 것은 파괴적 동작이고, 안전장치 없이 열면 되돌릴 수 없는 사고가 난다. 그래서 기본 복구를 비파괴적 경로로 정의하고 시작했다.

## 핵심 내용

### 개별 작업 기록 (시간순)

- 과거 버전 read-only 미리보기 (AC-01)
  - 버전 행에서 과거 스냅샷을 read-only로 여는 표면을 붙였다. 새 미리보기 컴포넌트를 만들지 않고 기존 `DetailPreviewSurface`를 그대로 재사용해, 배경과 fit 컨트롤이 현재 미리보기와 완전히 같게 유지했다. 같은 페이지를 보는 두 표면이 서로 다르게 동작하면 그 자체가 혼란이라, 차이는 오직 "과거임을 알리는 배지"로만 두었다. 배지에는 version, actor, 저장 시각을 싣고 시각 표기는 DetailRoute 헤더와 같은 ko-KR 형식을 썼다.
  - 여기서 한 가지 놓치기 쉬운 지점이 있었다. 스냅샷이 비어 있을 때 기존 EmptyState는 "편집해서 시작하세요"를 권한다. 과거 상태에 그 유도가 뜨면 사용자는 지금 페이지를 고치게 된다. 그래서 historical일 때는 전용 빈 상태를 따로 렌더해 편집 유도를 제거했다.
  - 스냅샷 조회 API는 없는 버전에 대해 404를 그대로 돌려주게 했다. 현재 data로 위장해서 채워주면 사용자는 과거를 보고 있다고 믿게 되므로, 없는 것은 없다고 말하는 쪽이 맞았다.

- structural diff 순수 헬퍼 작성 (AC-02)
  - `version-diff.ts`를 React나 fetch 없이 순수 함수로 분리했다. 유닛 테스트로 전부 검증 가능해야 한다는 게 이 파일의 존재 이유였다. 비교 대상은 스냅샷의 `data` 서브트리(`data.root.props`, `data.content`, `data.zones`)뿐이다.
  - 보고하는 변경은 다섯 가지다. 노드 추가, 노드 삭제, type 변경, prop 변경, 자식 순서 변경. 같으면 "변경 없음"으로 끝낸다.
  - 정규화 규칙을 딱 두 가지로 못 박은 게 이 작업의 핵심 판단이었다. 첫째, 페이지 메타(`version`·`updatedAt`·`updatedBy`·`previewContent`)는 저장마다 반드시 바뀌므로 애초에 `data` 밖에 있고, 여기서는 읽지 않는다. 그래서 "저장은 했지만 내용은 그대로"가 자연스럽게 "변경 없음"이 된다. 타임스탬프성 노이즈를 지우는 코드를 따로 쓸 필요가 없었다. 둘째, node `props.id`는 값 비교에서 제외하되 매칭 anchor로만 쓴다. id는 생성된 식별자이므로, 구조가 같고 id만 전부 재발급된 두 스냅샷(복제본이나 복구본)은 "변경 없음"이어야 한다.
  - 규칙을 두 개로 제한한 이유를 파일 주석에 남겼다. 정규화 규칙을 늘리기 전에 실제 데이터에 그 노이즈가 있는지 먼저 확인해야 한다는 것. 존재하지 않는 노이즈를 지우는 코드는 실제 변경을 숨긴다.
  - 자식 매칭은 2패스로 짰다. 먼저 양쪽에 유일하게 존재하는 같은 id끼리 짝짓고, 남은 것끼리 같은 type 안에서 순서대로 짝짓는다. id 중복이 있으면 anchor로 쓰지 않았는데, 중복 id를 신뢰하면 엉뚱한 노드끼리 짝지어져 실제와 다른 diff가 나오기 때문이다. id 우선 매칭이라 재정렬은 이동으로 읽히고, id가 전부 달라도 2패스가 구조를 붙잡는다.
  - prop 값 비교에는 키 순서에 무관한 안정 직렬화를 썼다. 객체 키 순서 차이를 변경으로 오인하면 diff가 노이즈로 뒤덮인다.
  - `path` 표기는 "그 노드가 실제로 있는 쪽" 기준으로 정했다. 추가는 오른쪽(b) 인덱스, 삭제와 변경은 왼쪽(a) 인덱스다. 이 규칙 때문에 한 위치에서 교체가 일어나면 추가와 변경이 같은 경로 문자열로 보일 수 있는데, 이건 감추기보다 주석으로 명시하는 쪽을 택했다.
  - 테스트는 219줄을 붙였다. 메타만 다른 경우, id만 재발급된 경우, id도 내용도 바뀐 경우, 스냅샷 전체와 data만 넘긴 경우의 동치, 객체 키 순서 차이, 추가/삭제/전부 삭제, type 변경 시 props를 파고들지 않는 것, prop 삭제를 undefined로의 변경으로 보고하는 것까지 각각 케이스로 잡았다.

- 새 draft 복구 경로 (AC-03)
  - `recoverVersionAsDraft`를 만들었다. 선택한 스냅샷의 data로 독립 draft(v1.0.0)를 생성하고, 출처를 `recoveredFrom:{slug,version}`으로 새 파일에만 기록한다. 원본 page JSON, history 사이드카, 스냅샷은 전부 읽기만 하므로 바이트 단위로 불변이고, 새 draft에는 "created" 이벤트 한 건만 생긴다.
  - 여기서 자잘하지만 실제로 걸리는 제약이 두 개 있었다. slug 힌트에 semver의 점이 들어갈 수 없어(SLUG_RE) 점을 하이픈으로 바꿔야 했고, 64자를 넘기면 서버가 힌트를 통째로 버리고 `page-<timestamp>`로 떨어지므로 미리 잘라야 했다. 서버가 조용히 폴백하는 지점은 클라이언트에서 먼저 맞춰두는 게 낫다.
  - `derivedFrom`은 일부러 전달하지 않았다. 복구본은 ejected 계보를 물려받는 게 아니라 독립 draft여야 하기 때문이다. `recoveredFrom`과 `derivedFrom`은 같은 `{slug,version}` 형태와 같은 검증(`normalizeDerivedFrom`)을 공유하지만 의미는 완전히 독립이라, 둘 다 가진 페이지도 성립한다는 걸 테스트로 못 박았다.
  - 서버 쪽에서는 `recoveredFrom`이 생성 시점의 출처 기록이라 저장으로 바뀌지 않게 했다. 저장 핸들러는 body를 보지 않고 기존 값을 보존만 한다. 목록 요약(PageSummary)과 상세 화면(InfoRow "복구 출처")에도 노출했다.
  - slug 형식이 아닌 복구 출처는 버린다는 것도 테스트로 잡았다. `../escape` 같은 값이 그대로 들어오면 경로 주입이 된다.

- 제자리 복원을 만들지 않기로 한 결정 (AC-04)
  - in-place restore, 즉 현재 페이지를 과거 버전으로 되돌리는 액션과 엔드포인트는 만들지 않았다. 이 파괴적 경로를 안전하게 열려면 네 조건이 필요하다고 봤다. diff 리뷰를 강제할 것, 정확한 확인문을 입력받을 것, 복구 직전 현재 상태의 스냅샷을 남길 것, 낙관적 baseVersion으로 동시 편집 충돌을 막을 것.
  - 이날 그 네 가지를 모두 갖출 수 없었으므로 버튼 자체를 만들지 않았다. 대신 기본 복구를 항상 "새 draft"로 두어 원본이 불변이 되게 했다. 안 만든 이유를 컴포넌트 주석과 커밋 본문에 남겨두어, 나중에 이 기능을 요구받았을 때 조건부터 확인하고 시작하게 했다.

## 정리

하루 전체가 사실 하나의 질문에 대한 답이었다. 이미 저장해두고 있던 불변 스냅샷을 어떻게 사람이 쓸 수 있는 도구로 만들 것인가.

세 개의 기능을 붙였지만 관통하는 원칙은 "원본을 읽기만 한다"였다. 미리보기는 스냅샷을 실제로 읽어 그리고 현재 data로 대체하지 않는다. diff는 순수 함수라 아무것도 쓰지 않는다. 복구는 새 파일을 만들 뿐 원본 page와 history와 스냅샷을 바이트 단위로 그대로 둔다. 이 원칙 덕분에 세 기능 모두 "잘못 눌러도 되는" 동작이 됐고, 그래서 안전장치를 최소한으로 유지할 수 있었다. 반대로 제자리 복원만이 이 원칙을 깨는 유일한 동작이었고, 그래서 유일하게 만들지 않은 기능이 됐다.

diff의 정규화 규칙을 두 개로 제한한 게 이날 가장 오래 고민한 지점이다. 정규화는 언뜻 많을수록 좋아 보인다. 노이즈를 더 지우면 사용자가 보는 diff가 더 깨끗해지니까. 그런데 정규화 규칙 하나하나가 결국 "이 차이는 무시해도 된다"는 단정이고, 그 단정이 틀리면 실제 변경을 조용히 숨긴다. 특히 diff는 "변경 없음"이라는 답을 내놓는 도구라, 틀린 "변경 없음"은 아무 경고 없이 사용자를 오도한다. 그래서 노이즈를 제거하는 규칙은 실제 데이터에 그 노이즈가 있다는 걸 확인한 뒤에만 추가한다는 원칙을 파일 주석으로 남겼다. 메타를 `data` 밖에 두는 설계가 이미 타임스탬프성 노이즈를 구조적으로 없애줬다는 것도 이날 다시 확인한 사실이다. 데이터 구조가 잘 잡혀 있으면 정규화 코드가 애초에 필요 없다.

id를 값 비교에서는 빼고 매칭 anchor로만 쓴 것도 같은 맥락이다. 생성된 식별자는 그 자체로는 의미가 없지만 "같은 노드"를 알려주는 힌트로는 가장 강력하다. 다만 중복 id는 anchor로 쓰지 않는다는 단서를 달아야 했다. 강한 힌트일수록 틀렸을 때 피해가 크다.

만들지 않기로 한 기능에 대해 조건을 명시적으로 적어둔 것은, 나중에 "이거 왜 없어요"라는 질문이 왔을 때 "안 만들었다"가 아니라 "이 네 가지가 갖춰지면 만든다"로 답할 수 있게 하기 위해서였다. 안 만든 이유가 코드에 없으면 다음 사람은 그냥 만든다.
