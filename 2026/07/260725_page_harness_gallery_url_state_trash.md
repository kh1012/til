# 상태의 단일 진실을 URL과 파일 위치에 두기

> 갤러리의 검색·필터·정렬을 URL 하나로 복구할 수 있게 만들고, 페이지의 휴지통 상태를 JSON 플래그가 아니라 파일 위치로 표현한 날.

## 배경

page-harness 페이지 갤러리는 페이지가 늘어날수록 "지금 보고 있는 목록"이 컴포넌트 로컬 state에만 살아 있는 게 문제였다. 새로고침하면 날아가고, 동료에게 링크로 공유할 수도 없다. 그래서 검색어·스테이지·정렬·보기 방식을 전부 URL로 끌어올리는 작업부터 시작했다.

같은 흐름에서 페이지 생명주기도 손댔다. 지금까지 삭제는 되돌릴 수 없었는데, 편집 도구에서 되돌릴 수 없는 삭제는 사용자를 겁먹게 한다. 여기에 히스토리 타임라인의 가독성 문제와, 히스토리의 version 번호가 가리킬 실제 과거 상태가 없다는 구멍까지 이어졌다.

두 작업 모두 결국 같은 질문이었다. 이 상태의 단일 진실(single source of truth)을 어디에 둘 것인가.

## 핵심 내용

### 개별 작업 기록 (시간순)

- 갤러리 검색·필터·정렬 상태를 URL canonical 로
  - q(자유 텍스트), stage, sort, dir, view, actor/preset/source 스코프, starred를 쿼리 파라미터 계약으로 정의했다.
  - 규칙은 두 가지다. 모르는 값과 빠진 값은 문서화된 기본값으로 정규화하고, 직렬화할 때는 기본값을 생략한다. 그래서 `parse(serialize(x)) === x`이고 serialize가 멱등이다.
  - 멱등성이 중요한 이유는 무한 루프 방지다. 같은 상태로 다시 navigate 해도 URL 문자열이 안 바뀌어야 replace/push가 서로를 다시 부르지 않는다.
  - dir은 sort별 기본 방향을 따로 뒀다. updated는 최신 먼저(desc), name은 A-Z(asc). dir이 없거나 이상하면 sort의 기본 방향으로 되돌린다.
  - 최근 검색어 저장소도 함께 만들었다. storage 실패(사파리 프라이빗, 용량 초과, 차단)에도 검색 자체는 계속 동작해야 하므로, 읽기는 storage 우선에 실패 시 메모리, 쓰기는 메모리를 먼저 갱신하고 storage는 best-effort로 시도한다.

- 갤러리 최근 검색 제안(빈 상태 focus·키보드 선택·전체 삭제)
  - 검색창이 비어 있는 상태에서 포커스하면 최근 검색어를 제안하고, 방향키로 선택하고, 전체 삭제할 수 있게 했다. 최신순 unique 최대 5개, 대소문자 무시로 중복을 걸러내되 표시는 최신 입력 형태를 쓴다.

- 계보 그룹핑을 group=lineage 별도 파라미터로
  - 계보 그룹핑(draft 아래 자기 ejected 자식을 묶기)을 view에 얹지 않고 group이라는 별도 파라미터로 뺐다. 그룹핑은 레이아웃(grid/list)과 다른 차원이라 어느 레이아웃에서도 켤 수 있어야 한다.
  - 핵심은 결과 집합 안에서만 묶는다는 점이다. 검색·필터로 좁힌 범위를 무시하고 전체 트리를 끌어오면 사용자가 정한 스코프를 앱이 임의로 넓히는 셈이 된다. 원본을 결과에서 찾을 수 없는 ejected는 orphan으로 남긴다.
  - 같은 이유로 검색 시 stage를 자동으로 all로 되돌리던 동작도 없앴다.
  - 입력 순서는 보존한다. 정렬 결과가 그룹 순서와 그룹 내부 순서를 계속 지배하게.

- 검색 결과 없음 상태 리디자인(halo·두 CTA·role=status)
  - 페이지가 있지만 질의와 매칭이 없는 경우를 실제 0건 빈 상태와 구분해서 다시 그렸다. 144px 원형 radial halo에 32px 아이콘, role=status로 스크린리더에 알린다.
  - 문구에 쓰는 검색어를 타이핑 중인 값이 아니라 settled 값(URL의 q)으로 바꿨다. 타이핑 중 새 글자를 섞어 보여주면 "없다"고 단정한 대상이 실제 판정 대상과 달라진다.
  - CTA를 두 개 뒀다. "전체 보기"는 입력값과 URL의 q를 함께 비우고 stage를 all로 되돌린 뒤, 사라지는 버튼에 포커스가 남지 않도록 비워진 검색 input으로 포커스를 옮긴다. "검색어 수정"은 질의를 보존한 채 input을 포커스하고 전체 선택해서 바로 갈아치울 수 있게 한다.
  - 진입 애니메이션은 일부러 넣지 않았다. 검색은 반복 UI라 매 질의마다 페이드가 튀면 피로하다.

- 페이지 soft-delete·휴지통·복원 생명주기
  - 상태의 단일 진실을 파일 위치(`pages/` ↔ `pages/.trash/`)로 두고 전이를 rename으로 수행했다. 그러면 slug·version·data·history 사이드카가 바이트 단위로 보존된다. 페이지 JSON 안에 플래그를 넣지 않으므로 해시가 바뀌지 않고, 위치와 플래그가 어긋날 여지도 없다.
  - 낙관적 동시성(baseVersion), 멱등 재호출, slug 충돌 시 자동 rename 거부를 갖췄다. 버린 시각·주체와 영구삭제 묘비는 slug 정규식을 통과하지 못하는 이름의 메타 파일에 따로 기록한다.
  - 활성 목록 요약에 계보 상대 상태를 실어서 "휴지통에 있음"과 "원본이 삭제됨"을 구별할 수 있게 했다.
  - UI 원칙 하나를 세웠다. 가역 동작에는 확인 다이얼로그를 두지 않는다. 휴지통 보내기는 실행취소 토스트로 끝내고, 영구삭제만 slug를 정확히 입력하는 확인 다이얼로그를 요구한다(서버에서도 재검증).
  - 통합 테스트 14건으로 바이트 불변(sha256 대조), 충돌, 묘비, 무관 파일 안전을 검증했다.

- 히스토리 타임라인 필터·prompt grouping·bounded 로딩
  - action/actor 필터 칩을 붙였다. actor 칩은 2명 이상일 때만 나온다. 보이는 개수와 전체 개수를 접근 가능한 상태 텍스트로 알린다.
  - 같은 version에 인접한 prompt 로그를 "프롬프트 N회" 한 행으로 접고, 상세에 actor·상대/절대 시각·note를 보존했다.
  - 최초 20 논리 행을 그리고 "이전 기록 더 보기"로 20개씩 붙인다. 마지막 배치에서 첫 새 행으로 포커스를 옮겨 키보드 흐름이 끊기지 않게 했다.
  - disclosure 헤더에 안정적인 panel id로 aria-controls를 걸고, 접힘은 hidden으로 처리해 focusable 트리에서 아예 제거했다. 스켈레톤 pulse에는 motion-reduce를 붙였다.

- 320px 검색 빈 상태 설명 clip 해소
  - 리뷰 지적이었다. line-clamp-2가 320px 화면(컨테이너 208px)에서 두 CTA를 설명하는 뒷문장을 통째로 잘라먹었다.
  - 검색어는 길이 제한 없는 사용자 입력이라 어떤 문구로도 208px 2줄을 보장할 수 없다. 그래서 clamp를 sm 이상에서만 적용하고 좁은 폭에서는 줄 수를 풀었다. 끊을 곳 없는 긴 토큰은 overflow-wrap:anywhere로 접어 수평 overflow를 막았다.
  - 320x720 실뷰포트에서 측정했다. baseline은 4개 질의 전부 clip이었고(scrollHeight가 clientHeight를 넘고 뒷문장 미표시), 수정 후에는 전부 3~5줄로 뒷문장이 보이고 수평 overflow도 없었다.

- 버전 스냅샷 저장소·백필 CLI·읽기 API
  - 히스토리의 version 번호가 가리킬 실제 과거 페이지 상태를 `pages/.versions/<slug>/<version>.json`에 불변 기록한다. 쓰기는 항상 O_EXCL이라 같은 (slug, version) 조합은 덮이지 않는다.
  - 생성과 버전 올림 저장마다 페이지 쓰기와 같은 락 안에서 스냅샷 1건을 남긴다. prompt 로그와 실패한 저장(409)은 스냅샷을 만들지 않는다.
  - CLI에 versions 커맨드를 붙여 목록 조회와 백필을 지원했다(dry-run, slug 지정, 멱등). 스냅샷이 하나도 없는 페이지에 현재 버전만 백필하고 기존 page/history는 읽기만 한다.
  - 읽기 API는 메타 목록(data 미포함)과 정확한 불변 스냅샷 두 갈래다. 없는 스냅샷을 current로 위장하지 않고 404를 준다. 비-semver와 traversal은 400.
  - 라이브 dev-server로 실측했다. 연속 저장 후 앞선 스냅샷의 sha256이 불변이고, prompt와 409는 개수를 늘리지 않으며, 무관 파일의 바이트도 그대로였다. 유닛 18건을 새로 붙였다.
  - 계획의 일부 AC만 이 커밋에 담겼다는 사실을 커밋 메시지에 명시하고 나머지는 핸드오프로 넘겼다. 다 한 척하지 않는 게 다음 사람에게 더 낫다.

## 정리

하루를 관통한 질문은 "이 상태를 어디에 적어야 어긋나지 않는가"였다. 갤러리 쪽에서는 답이 URL이었고, 페이지 생명주기 쪽에서는 파일 위치였다.

URL을 단일 진실로 삼을 때 배운 건, 정규화와 직렬화를 대칭으로 짜면 공짜로 얻는 게 많다는 것이다. 모르는 값을 기본값으로 접고 기본값은 직렬화에서 생략하면, `parse(serialize(x)) === x`가 성립하고 serialize가 멱등이 된다. 그러면 "같은 상태로 다시 이동"이 문자열 비교 한 번으로 걸러져서 라우터 루프가 구조적으로 안 생긴다. URL이 짧아지는 건 덤이었다.

휴지통 쪽은 더 재밌었다. 처음에는 페이지 JSON에 `deleted: true` 플래그를 넣는 게 자연스러워 보였는데, 그러면 파일 내용이 바뀌어 해시가 달라지고 "위치는 활성인데 플래그는 삭제"같은 어긋난 상태가 표현 가능해진다. 상태를 파일 위치로 옮기고 전이를 rename으로 하면 그 어긋남 자체가 표현 불가능해진다. 사이드카까지 바이트 단위로 보존되는 것도 같은 선택의 결과였다. 잘못된 상태를 "검사해서 막는" 것보다 "애초에 만들 수 없게" 하는 쪽이 언제나 낫다.

빈 상태의 320px clip 건은 다른 종류의 교훈이었다. line-clamp-2는 문구를 내가 고정할 수 있을 때만 안전한 도구다. 검색어처럼 사용자가 길이를 정하는 값이 문장에 섞이면, 어떤 문구를 써도 특정 폭에서 잘리는 지점이 반드시 생긴다. 좁은 폭에서는 clamp를 아예 풀어버리는 게 정답이었다. 그리고 이걸 실뷰포트에서 scrollHeight와 clientHeight를 직접 재서 확인했다는 점도 남겨둘 만하다. "잘리는 것 같다"와 "4개 질의 전부 잘렸다가 전부 안 잘린다"는 다른 수준의 근거다.
