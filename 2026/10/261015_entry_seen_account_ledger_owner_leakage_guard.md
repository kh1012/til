# 읽음 기록을 로컬스토리지 전용에서 계정 동기화로 옮기며, 같은 브라우저의 계정 교체 시 이전 계정 읽음 기록이 새 계정으로 새는 것을 OWNER_KEY로 막은 설계

> atelier의 "안 본 변경사항" 표시 기능은 그동안 `entry-seen.ts`가 브라우저 localStorage에만 읽음 기록을 저장했다. 기기를 바꾸면 이미 본 변경사항이 다시 "안 본 것"으로 뜨는 문제가 있어, 읽음 기록을 계정의 `/api/user-settings` 아래로 옮기는 작업을 했다. 이 과정에서 로컬 상태와 서버 상태를 합칠 때 "같은 브라우저를 다른 계정이 쓴 경우" 데이터가 섞이는 문제가 새로 생겼고, 이를 `OWNER_KEY` 하나로 막았다.

## 배경

요구사항은 사용자 발화 그대로였다 — "변경된걸 열어봤으니 … 이제 변경된게 아닌거 아니야?" 즉 한 번 열람한 항목은 다시 "변경됨" 표시가 뜨면 안 된다는 것. 기존 구현은 이 요구를 로컬스토리지 하나로 충족했지만, 기기 간 동기화가 빠져 있었다.

읽음 기록을 서버로 옮기는 순간 "병합" 문제가 생긴다. 서버 응답(계정에 저장된 기록)과 브라우저에 남아있는 로컬 기록 중 어느 쪽을 믿을지 정해야 한다. 거기에 더해 atelier 워크벤치는 같은 브라우저를 여러 사람이 돌아가며 쓰는 환경(사무실 공용 PC, 테스트 계정 전환)이라 "브라우저에 남은 기록이 지금 로그인한 사람의 것이 아닐 수 있다"는 조건까지 같이 풀어야 했다.

## 핵심 내용

**저장 위치 이동**: `entry-seen.ts`가 들고 있던 로컬 기록 로직은 그대로 두고, `entry-seen.account.ts`를 새로 만들어 계정 쪽 ledger 파싱·정리(40KB 넘으면 오래된 것부터 제거)·동기화 헬퍼를 분리했다. 기존 로컬 전용 코드를 버리지 않고 계정 레이어를 얹은 구조다.

**병합 규칙 — newer-time-wins**: 서버가 내려준 ledger와 로컬에만 있는 최신 기록(마지막 동기화 이후 새로 읽음 처리된 항목)을 항목별로 비교해서 더 늦은 타임스탬프를 남긴다. 어느 한쪽을 통째로 덮어쓰지 않고 항목 단위로 합친다.

**OWNER_KEY — 계정 교체 누수 차단**: 브라우저에 로컬로 남아있는 읽음 기록이 지금 로그인한 계정의 것인지 구분할 방법이 없으면, 병합 규칙이 그대로 사고로 이어진다. A 계정이 쓰던 브라우저에서 B 계정으로 로그인하면, newer-time-wins 병합이 A의 로컬 읽음 기록을 B의 서버 기록과 섞어버려 B 쪽에 "B가 보지도 않은 항목이 읽음 처리된" 상태가 새어 들어간다. 이를 막으려고 로컬 저장소에 `OWNER_KEY`로 마지막 접속 계정을 같이 기록해두고, `loadAccount()`가 들어오는 계정과 `OWNER_KEY`가 다르면 병합을 시도하지 않고 브라우저 쪽 상태를 통째로 버린 뒤 서버 데이터로 교체한다. "항목 단위 병합"과 "계정 단위 전량 폐기"를 조건 하나로 가른 것이 이 설계의 핵심이다.

**요청 배치 — 400ms 묶음 전송**: 항목을 연속으로 열어볼 때마다(⌘K로 여러 개 빠르게 열람 등) 매번 POST를 보내면 "읽음 N번 = 요청 N번"이 된다. 마크 호출을 400ms 타이머로 모아서 "읽음 N번 = 요청 1번"으로 줄이되, 브라우저가 닫히기 전에는 반드시 flush되도록 처리했다.

**로딩 — 최초 구독 시점 1회, 이후 캐시 재사용**: `useSeenLedger` 훅을 구독하는 컴포넌트가 여러 곳(Space, 상세 카드, ⌘K, 탭, 직접 주소 접근, 컴포넌트 워크스페이스, Fast 페이지)에 흩어져 있다. 각자 마운트 시점에 계정 데이터를 불러오면 동시에 여러 요청이 뜨는 thundering herd가 생긴다. 첫 구독에서만 `loadAccount()`를 호출하고 이후 구독은 캐시된 결과를 재사용하도록 했고, 닉네임이 바뀌거나(다른 사람 계정) 포커스가 돌아올 때(서버 쪽에서 동기화됐을 수 있음)만 강제로 다시 불러온다.

## 정리

로컬 전용 기능을 서버 동기화로 확장할 때 "병합을 어떻게 할까"만 보기 쉬운데, 실제 위험은 "병합 대상이 같은 사람의 데이터가 맞는가"를 먼저 확인하지 않는 데서 나온다. 이번 설계는 그 확인을 `OWNER_KEY` 비교로 명시적인 조건으로 만들어, 조건이 깨지면 병합이 아니라 전량 폐기로 분기하게 했다. 같은 브라우저를 여러 계정이 공유하는 환경에서 로컬 캐시를 서버와 합치는 기능을 또 만들 일이 있으면, "누구의 로컬 상태인가"를 먼저 식별하는 키를 같이 저장해두는 패턴을 다시 쓸 수 있다.
