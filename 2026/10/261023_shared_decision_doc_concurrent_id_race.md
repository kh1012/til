# 여러 Claude Code 세션이 같은 git 저장소의 같은 결정 기록 문서에 동시에 번호(D196)를 매겨 충돌한 사례

> `apps/atelier/docs/2026-10-19-builder-concept.md`에 결정 사항을 `D<N>`으로 번호 매겨
> 누적 기록하는데, 다음 번호를 파일을 읽어서 추정하는 방식이라 같은 저장소에서 동시에
> 작업하던 두 세션이 똑같이 D196을 붙였다. 예약 없는 번호 매기기는 동시 세션 수만큼
> 겹칠 확률이 있다.

## 배경

Atelier의 "builder" 개념 설계를 브레인스토밍하며 결정 사항을 `D<N>` 형식으로 문서에
계속 덧붙이는 작업 방식을 쓰고 있었다. 한 세션이 결정 14건(D196~D209로 추정)을 작성해
커밋하는 동안, 같은 클론을 쓰는 다른 세션이 별도로 썸네일 관련 결정 하나를 똑같이
D196으로 커밋했다.

## 핵심 내용

- 세션 A: `f74c8637`(00:02) → D195, 이어서 `12422c11`(00:20) → D196(썸네일 결정,
  `2026-10-23-builder-figma-mockups.html`).
- 세션 B(이 세션): 독립적으로 D196부터 시작하는 결정 14건을 작성해 `4a01ecb8`(00:17:40)
  → "D196 ~ D209"로 커밋. 커밋 시각이 세션 A의 두 커밋 사이에 끼었다.
- 충돌을 알아챈 시점은 작업이 끝난 뒤 `git log`를 다시 확인했을 때다. 같은 D196이
  서로 다른 내용(썸네일 결정 vs 세션 B의 첫 결정)으로 두 번 존재했다.
- 근본 원인: "다음 사용 가능한 D 번호"를 파일 내용을 읽어서 추정했다. 원자적으로
  예약하는 락이나 카운터가 없는 자유 텍스트 문서라, 동시에 같은 시점의 파일 상태를
  읽은 두 세션이 똑같은 다음 번호를 고른다.
- 복구: 다른 에이전트 세션에 연락할 방법이 없음을 `ListAgents`로 확인한 뒤, 세션 B가
  자기 쪽 14건을 정규식 기반 Python 스크립트로 D197~D210으로 일괄 재번호. 결정 개수
  정확히 맞는지, 중복 D196이 남지 않았는지 assert로 검증하고 `prettier --check` 통과
  확인 후 `920149f`로 커밋. 커밋 메시지에 충돌 경위를 그대로 남겼다.
- 같은 세션이 이 실패 양상을 다음 세션도 알 수 있도록 `shared-doc-decision-number-race.md`
  메모리 노트로 남겼다.

## 정리

- 공유 저장소에서 여러 에이전트 세션이 동시에 돌 수 있는 구조라면, 순번을 "파일을
  읽어서 다음 값을 추정"하는 방식은 세션 수만큼 충돌 확률이 생긴다. 원자적 카운터나
  락이 없는 한 항상 재번호 복구 경로를 준비해 둬야 한다.
- 충돌은 당시 알아챌 방법이 없었고, 사후에 `git log`를 다시 읽었을 때만 드러났다 —
  동시 작업 중인 다른 세션의 존재를 사전에 감지할 수단(`ListAgents` 등)은 있었지만,
  파일을 쓰는 시점에 그 번호가 이미 쓰였는지 확인하는 절차 자체가 없었다는 게 더
  근본적인 공백이다.
