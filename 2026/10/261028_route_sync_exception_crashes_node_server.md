# 라우트 핸들러 안의 동기 예외 하나가 Node 서버 프로세스 전체를 죽이는 문제를, 핸들러를 감싸는 request-guard 래퍼로 막은 사례

> plugin-builder 서버에서 썸네일 쓰기 하나가 EPERM으로 실패했을 때, 그 동기 예외가 라우트 핸들러를 빠져나가 `createServer` 콜백까지 전파되며 Node 프로세스 자체를 죽였다. 슈퍼바이저가 60초 안에 5번까지 재시작을 시도하다 그 이상이면 재시작을 멈춘다. 이를 막기 위해 모든 라우트 핸들러를 감싸는 `guardRequests()` 래퍼(`apps/builder/server/lib/request-guard.ts`)를 추가했다.

## 배경

atelier 테스트 중 썸네일 파일 쓰기가 권한 오류(EPERM)로 실패하는 상황이 있었다. 문제는 단순히 그 요청 하나가 실패하는 데서 끝나지 않았다 — 핸들러 안에서 처리되지 않은 동기 예외가 그대로 위로 던져지면서 서버를 띄우는 `createServer` 콜백까지 전파됐고, Node 프로세스가 통째로 죽었다. 서버는 슈퍼바이저 스크립트가 다시 띄워주지만, 60초 안에 5번 넘게 죽으면 슈퍼바이저도 재시작을 포기하고 멈춘다. 결국 라우트 하나의 예외 처리 누락이 서비스 전체 중단으로 번질 수 있는 구조였다.

## 핵심 내용

**문제의 범위 — 동기 예외만**: `guardRequests()`가 잡는 것은 라우트 핸들러가 동기적으로 던지는 예외다. 요청 본문을 다 받은 뒤(`req.on("end")` 이후) 비동기로 발생하는 예외는 이 래퍼를 거치지 않는다 — 그건 각 라우트가 `readJson` 에러 처리로 직접 잡아 400을 돌려주는 책임으로 남겨뒀다. 가드와 라우트별 에러 처리를 이중으로 겹치지 않게 역할을 나눈 것이 핵심이다.

**응답 상태에 따라 분기**: 예외를 잡은 뒤 헤더가 아직 안 나갔으면 500 JSON 응답을 보내고, 이미 헤더가 나간 뒤라면(스트리밍 중 등) 응답을 더 보낼 수 없으므로 연결을 강제로 끊는다(`destroy`). 둘 다 예외 스택트레이스를 메서드·URL과 함께 로그로 남겨 사후 추적이 가능하게 했다.

**왜 라우트 하나하나에 try/catch를 안 넣었나**: `apps/builder/server/repo-routes.ts`, `remove-routes.ts`, `snapshot-routes.ts`, `thumb-routes.ts`, `unit-make-routes.ts`, `unit-routes.ts` 등 라우트 파일이 여러 개로 흩어져 있다. 이 모두에 개별적으로 예외 처리를 넣는 대신, 모든 핸들러가 공통으로 거치는 지점에 래퍼 하나를 씌워 "새 라우트를 추가해도 이 보호가 자동으로 적용된다"는 구조로 만들었다.

## 정리

하나의 요청 처리 실패가 프로세스 전체를 죽이고, 그 죽음이 반복되면 슈퍼바이저의 재시작 한도(5회/60초)까지 소진시켜 서비스가 완전히 멈추는 연쇄를 봤다. 파일 쓰기 권한처럼 평소엔 거의 안 일어나지만 환경에 따라 터질 수 있는 동기 예외는, 발생 지점마다 막기보다 요청 처리 공통 경로에 가드를 씌워 막는 쪽이 새 코드가 추가돼도 보호가 깨지지 않는다. 다만 가드가 막는 범위(동기 예외)와 각 라우트가 책임져야 하는 범위(비동기 예외)를 명확히 나눠야 같은 예외를 두 군데서 처리하거나 반대로 아무 데서도 안 잡는 구멍이 안 생긴다.
