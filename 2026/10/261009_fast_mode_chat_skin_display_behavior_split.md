# Fast 모드 채팅 패널에 CLI 감성 테마를 적용하기로 하면서, 즉시 구현 대신 화면 표시와 동작 로직을 분리해 미루는 두 단계 설계로 확정

> atelier의 Fast 모드는 "CLI처럼 빠르다"는 정체성을 시각적으로도 드러내기 위해 OpenCode CLI의 색상·커서·스캐너 애니메이션을 채팅 패널에 적용하기로 했다. 다만 Fast 모드 핵심 구현(Shell 개편 TS-C1 등)이 아직 진행 중이어서, 테마 작업을 바로 붙이지 않고 설계만 먼저 확정한 뒤 핵심 구현 완료 후로 미뤘다. 핵심은 "표시"와 "동작"을 분리하는 구조 — `data-chat-skin="basic"|"opencode"` 속성으로 화면만 `.basic.tsx`/`.cli.tsx` 두 변형으로 나누고, 전송·수신·버전 로직 같은 동작은 `useFastComposer` 훅 하나를 그대로 공유한다.

## 배경

Fast 모드와 Agentic 모드 모두 채팅 패널을 쓰지만, Fast 모드만 먼저 CLI 감성 테마(어두운 배경 `#0a0a0a`, 밝은 배경 `#ffffff`, 블록 커서 점멸, 8×40ms 54프레임 스캐너 애니메이션, 회색 보조 텍스트 `#808080`)를 적용하기로 했다. 동시에 진행 중인 작업 스트림(Shell 개편 TS-C1, TS-C2, TS-C4)과 일정이 겹쳐, 테마를 바로 구현하면 핵심 기능 완성을 늦출 위험이 있었다. 이에 사용자는 구현에 들어가기 전에 설계 문서부터 작성해 범위와 순서를 먼저 못박았다.

## 핵심 내용

**구현을 즉시 하지 않고 설계부터 확정한 이유는 핵심 기능 완성 속도를 지키면서 디자인 일관성도 잃지 않기 위해서다.** Fast 모드 핵심 구현이 불안정한 상태에서 테마 레이어까지 얹으면 두 작업이 서로의 디버깅을 방해한다. 그래서 1단계(Shell 개편 TS-C1 이전) — 설정, 테마 토큰, 빈 화면 레이아웃, Fast 모드 테마 적용, 버전 타임스탬프, 입력창 스크롤 동작 — 와 2단계(TS-C1 이후) — Shell의 공유 채팅 컴포넌트를 재사용해 Agentic 패널에도 같은 테마를 입히는 작업 — 로 나누고, 핵심 구현과 테마 작업이 겹치는 구간을 없앴다.

**화면(display)과 동작(behavior)을 구조적으로 분리해, 테마 전환이 로직에 손대지 않게 했다.** 채팅 루트에 `data-chat-skin="basic"|"opencode"` 속성을 두고 CSS 캐스케이드로 외형을 바꾸는 한편, 실제 메시지 전송·수신·버전 처리 로직은 `useFastComposer` 훅 하나로 묶어 `basic.tsx`/`cli.tsx` 두 화면 변형이 동일하게 가져다 쓴다. 설정 UI도 `SettingCategory`에 `groups?: { label; description?; fields }[]`를 추가해 "채팅 패널 테마" 그룹을 만들고 Fast/Agentic 테마를 따로 고를 수 있게 했다(기본값: Fast는 opencode, Agentic은 basic).

**디자인을 확정하기 전에 WCAG 명암비를 먼저 검증했다.** 어두운 테마 최악 케이스(보조 텍스트) 4.68:1, 밝은 테마 최악 케이스(오류 텍스트) 4.59:1로, AA 기준 4.5:1을 모두 넘는지 구현 전에 확인해뒀다. 색상 선정이 끝난 뒤 뒤늦게 접근성 문제로 되돌아가는 일을 막기 위한 순서다.

## 정리

새 시각 테마를 기존 기능 위에 얹을 때, 구현부터 시작하면 테마 변경이 동작 로직까지 건드리게 되어 두 관심사가 뒤섞인다. 속성 하나(`data-chat-skin`)로 화면 변형을 나누고 동작은 훅 하나로 공유하는 구조를 먼저 설계해두면, 테마 추가·전환이 순수하게 CSS·레이아웃 레이어에서만 끝난다. 동시에 진행 중인 핵심 작업과 일정이 겹칠 때는 구현을 바로 하지 않고 설계 문서로 범위·순서·검증 기준(이번 경우 WCAG 명암비)을 먼저 못박아두는 것도, 나중에 두 작업이 서로를 밀어내지 않게 하는 방법이다.
